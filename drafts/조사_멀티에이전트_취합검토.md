# 조사: 멀티 에이전트 취합 · 검토 방법론과 에이전틱 설계 대조 (2026-11-14)

> 계기: white님 "여러가지 방법론 많을 거 같은데 조사도 좀 하고 그래봐"(11-14 16:11 KST), 앞 질문 "취합 검토 과정은?".

## 1. 찾은 방법론

| 방법론 | 요지 | 출처 · 신뢰 |
| :--- | :--- | :--- |
| 생성자-검증자(generator-verifier) | 만드는 쪽과 검증하는 쪽을 나눈다. 기준이 명시돼 있을 때만 효과가 있고, 반복 상한과 그 뒤 사람에게 넘기는 규칙이 필요하다 | Anthropic, Multi-agent coordination patterns(2026-04) · 신뢰 4 |
| 총괄-하위(orchestrator-subagent) | 총괄이 계획 · 분배 · 종합한다. 하위 작업이 서로 덜 얽힐 때 맞는다. 총괄이 정보 병목이 되고, 종합 때 세부가 요약되며 사라진다 | 같은 글 · 신뢰 4 |
| 에이전트 팀 · 메시지 버스 · 공유 상태 | 팀은 같은 파일을 동시에 고치면 충돌, 메시지 버스는 잘못 보내진 이벤트가 조용히 실패, 공유 상태는 중복 작업과 끝나지 않는 순환이 약점 | 같은 글 · 신뢰 4 |
| 결과는 저장소에, 총괄에는 참조만 | 하위 결과를 외부 저장소에 쓰고 총괄에는 가벼운 참조만 넘겨 '말 전하기 놀이'를 피한다. 검증은 별도 에이전트(인용 검증)와 LLM 채점, 그리고 사람 평가 | Anthropic, How we built our multi-agent research system(2025-06) · 신뢰 4 |
| 비용 | 에이전트는 대화의 약 4배, 멀티 에이전트는 약 15배 토큰을 쓴다. 코딩은 연구보다 병렬화할 몫이 적다 | 같은 글 · 신뢰 4 |
| 역할 SOP 파이프라인(ChatDev · MetaGPT) | 설계 · 코딩 · 리뷰(정적) · 테스트(동적)를 역할로 나눈 고정 절차. 리뷰와 테스트가 분리돼 있다 | 논문 소개 글들 · 신뢰 2~3 |
| 자유 종합의 환각 | 여러 결과를 자유 문장으로 합치면 없는 내용을 만든다. 항목별 표 · 투표처럼 정해진 틀로 합치라는 권고 | 업계 가이드 글 · 신뢰 2 |

## 2. 우리 설계와 맞는 곳

1. 판정 에이전트 분리 = 생성자-검증자. 기준이 정본이라 '기준 없는 검증자'(그냥 통과시키는 검증) 함정을 피한다.
2. GitHub를 유일한 작업판으로 둔 것 = 결과는 저장소에, 총괄에는 참조만. 총괄 병목 · 요약 손실을 구조로 피한다.
3. 같은 화면 한 번에 하나 = 팀 패턴의 파일 충돌 대책(작업 분할 · 잠금)과 같다.
4. 병렬로 펼치지 않고 TASK 1건 = 실행 1개 = 토큰 원칙과 맞다(멀티 에이전트 15배 비용 경고).

## 3. 빈 곳 셋과 보강안 (장치 덧대기 없이 규칙 한 줄씩)

| 빈 곳 | 근거 | 보강안 |
| :--- | :--- | :--- |
| ① 고침 반복의 상한이 없다. 판정이 ❌일 때 작성 에이전트가 고치고 다시 판정받는 고리가 끝없이 돌 수 있다 | 생성자-검증자의 반복 상한 · 사람에게 넘기기 | 같은 PR에서 작성 에이전트의 고침은 2회까지. 그 뒤에도 ❌면 `agent-failed`로 멈추고 PM 백로그로 간다 |
| ② 취합 판정이 자유 종합이면 환각 위험 | 자유 종합 환각, 요약 손실 | 취합 판정은 정본 변경분에서 POL · 화면 코드 목록을 먼저 기계로 뽑고(결정적), 판정 에이전트는 그 목록의 항목마다 ✅/❌만 적는다. 목록에 없는 항목을 만들지 않는다 |
| ③ 이벤트가 조용히 실패할 수 있다. 배정됐는데 실행이 안 뜬 TASK를 아무도 모른다 | 메시지 버스의 조용한 실패 | 새 알림을 만들지 않고, 이미 있는 `open_tasks.md`(열린 TASK 목록)에 "작성 에이전트 배정 · PR 없음" 칸을 더해 주간 회의에서 본다(9-6) |

- 덧붙임: 사람 평가가 자동 채점이 놓치는 것을 잡는다는 근거가 있어, 수준을 내린 뒤에도 주간 회의에서 판정 리포트 몇 건을 사람이 표본으로 본다. 9-8의 "뒤집힘 0건" 판단 재료가 된다.

## 4. 반영 제안

위 ①~③과 덧붙임을 오케스트레이션 설계 3 · 5절에 한 줄씩 넣는다(초안 5). 구조 층을 바꾸지 않는 보강이라 DDD 대조 뒤 white님 서명을 함께 받는다.

# 2차 조사: 최근 에이전틱 방법론 넓게 (2026-11-14)

## 5. 방법론별 요지와 우리 설계 대응

## 6. 이번 조사에서 나온 보강 둘

1. **구현 전 일관성 검사(Spec Kit analyze)**: 총괄이 TASK 후보를 올릴 때, 판정 에이전트가 그 TASK 묶음 ↔ 정본 변경분 ↔ 계약이 서로 모순되지 않는지 한 번 본다. 취합 판정(구현 뒤)과 짝이 되는 '구현 전' 판정이다. 새 역할이 아니라 판정 에이전트의 깨어나는 때 하나와 `task_split` 관문 내용으로 넣는다.
2. **실행당 비용 한도(12-Factor)**: 에이전트 실행마다 토큰 상한을 두고, 넘으면 멈추고 `agent-failed`로 PM에게 간다. 값은 다음 층(설정)에서 정한다.

## 7. 확인만 하고 넣지 않은 것

- 병렬 작성자 무리(swarm): 비용 15배, 충돌 위험, Cognition도 여전히 안 된다고 봄 → 넣지 않는다.
- 총괄의 자동 재계획(Magentic-One 바깥 고리): 사람 판단 원칙과 부딪힘 → PM에게 넘기는 지금 방식 유지.

# 3차 조사: 사내에 에이전틱이 여럿일 때 (관제 · 가드레일 · 보안) (2026-11-14)

> 계기: white님 "부서별이나 사업별로 여러 에이전틱이 생기고 … 나와 같은 고민을 하고 있지 않을까? 그래서 자료 조사도 좀 넓은 개념으로"(19:53 KST).
> 신뢰: 대부분 업체 · 컨설팅 글이라 신뢰 2~3. Gartner 보도자료는 4.

## 8. 업계가 수렴하는 그림: 등록부 · 관문 · 관제

| 구성 | 하는 일 | 호출 경로 | 출처 · 신뢰 |
| :--- | :--- | :--- | :--- |
| 등록부(registry) | 어떤 에이전트 · 도구(MCP 서버)가 있고, 누가 주인이고, 어느 판이 운영 중인지 적는 기록의 원본 | 밖(조회만) | Agent Registry 2026 Field Guide 등 · 신뢰 2~3 |
| 관문(gateway) | 에이전트와 모델 · 도구 사이에서 모든 호출을 중계하며 정책을 강제 | 안(호출마다) | TrueFoundry, obot.ai 등 · 신뢰 2~3 |
| 관제(control plane) | 정책의 원본. 관문은 관제가 정한 것을 집행하는 한 수단 | — | 같은 글들 · 신뢰 2~3 |

- 큰 업체들이 같은 방향으로 내놓고 있다고 보도됨: Microsoft Agent 365, Google Cloud(에이전트 신원 · 등록부 · 관문 · 평가 · 관측), IBM 관제 평면, ServiceNow(에이전트별 정지 스위치). 날짜 · 출시 상태는 출처마다 달라 미확인(신뢰 2).
- 사내 현실은 섞여 있다: Copilot · Agentforce · 자체 에이전트 · 업체 내장 AI가 함께 돈다. 그래서 등록부는 '우리가 만든 셀'만이 아니라 다른 에이전트도 담아야 한다는 주장(신뢰 2).

## 9. 가드레일은 에이전트 바깥에서

- OWASP 에이전틱 Top 10(2026) 해설들: 에이전트마다 자기 신원, 짧게 사는 자격, 실행 순간의 권한 판단, 모든 행동을 검사하는 정책 집행 층, 도구는 격리 환경 + 외부 통신 제한, 큰 영향은 사람 승인(신뢰 3, 원문 미확인).
- "어느 에이전트가 언제 무엇을 했는지 실행 순간에 보지 못하면 그것은 통제가 아니라 관찰이다"라는 주장(신뢰 2~3). 기록만 쌓는 모아 보기로는 가드레일이 안 된다는 뜻.

## 10. AI가 AI를 지켜보기(Gartner '가디언 에이전트')

- 정의: 다른 AI를 감시하는 AI. 2030년 에이전틱 시장의 10~15%로 예측(Gartner 2025-06 보도자료, 신뢰 4).
- 2026-02 시장 안내서 요약: 가시성 · 추적, 지속 평가, 실행 중 검사 · 집행. 감시받는 플랫폼과 **독립된** 감시를 권함(요약 글, 신뢰 3).

## 11. 우리 설계에 주는 뜻 (제 판단)

1. white님의 "파이프라인 · 관제 · 모니터링 · 전체 가드레일"은 업계의 등록부 · 관문 · 관제 셋과 거의 같은 자리다. 방향이 맞다는 근거로 본다.
2. 지금 11절(상위 층)에 **관문이 빠져 있다.** 모아 보기는 '관찰'이고, 보안 가드레일은 모델 · 도구 호출 경로 안에서 막아야 한다. 상위 층에 관문을 넣어야 한다.
3. AI 보조는 '가디언'(감시 · 검토 · 보호) 꼴로 들어간다. 판정 에이전트(셀 안 검사)와는 다른 역할: 실행 기록 · 관문 기록을 보고 이상 신호를 찾아 사람에게 알린다. 정지는 정해진 문턱이면 관문이 기계로, 그 밖은 사람이 한다.
4. 등록부는 다른 에이전트(Copilot 등)도 받아야 부서별 에이전틱이 늘어도 한 그림으로 본다. 셀이 아닌 에이전트는 '외부 에이전트'로 등록하고 관문만 거치게 한다.
5. 넣지 않을 것: 셀 사이를 A2A 같은 에이전트 간 대화로 잇는 것. 셀 사이는 지금처럼 작업판과 공개 계약으로 잇고, A2A는 조직 밖이나 외부 업체 에이전트와 관문에서 만날 때만 다시 본다.
6. 주의: 이것은 사내 플랫폼 규모의 일이라 문서 규약 저장소 하나의 범위를 넘는다. 개념 설계는 지금 하되, 구현은 셀 시범 뒤에 하고 관문 · 등록부는 업체 제품을 쓸지 만들지부터 정해야 한다.
