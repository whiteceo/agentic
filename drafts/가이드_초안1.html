제안 팀의 AI 활용 방식 · v1.0.0

AI를 각자 쓰는 팀에서
같은 기준으로 일하는 팀으로

기획자, 디자이너, 개발자가 저마다 AI를 쓰면 일은 빨라지지만 결과물은 서로 어긋나기 쉽습니다. 이 가이드는 모든 사람의 AI가 같은 기획 문서를 기준으로 일하게 만드는 방법을 제안합니다. 사람은 정하고 승인하는 일에 집중하고, 옮겨 적기와 대조, 반복 검사는 AI와 자동 검사가 맡습니다.

처음 보는 분은 1~5절만 읽어도 충분합니다. 점선 밑줄 단어는 마우스를 올리거나 누르면 풀이가 나옵니다.

01 · 왜 필요한가

AI를 각자 쓰면 결과물이 조금씩 어긋납니다

AI는 문서에 빈칸이 있으면 그럴듯한 답을 지어내 채웁니다. 한 사람이 쓸 때는 편리하지만, 여러 사람이 각자 쓰면 서로 다른 답이 쌓입니다. 이 가이드는 그때 반복되는 네 가지 문제를 줄이려고 만들었습니다.

⇢

기획과 다른 결과물

개발자의 AI가 기획서에 없는 할인 조건이나 상태를 짐작으로 만듭니다. 기획자는 출시 직전에야 알게 됩니다.

⇄

팀마다 다른 숫자

같은 '정산 금액'을 화면 개발자와 서버 개발자가 다르게 계산합니다. 여러 기획자가 동시에 일할수록 더 자주 생깁니다.

▦

제각각인 화면

AI가 화면을 빨리 만들어 주는 만큼, 버튼과 배치도 화면마다 조금씩 달라집니다.

◎

사람 눈에 기대는 검수

기획서와 결과물을 맞춰 보는 일을 사람이 전부 눈으로 하면, 검수가 늘 병목이 됩니다.

02 · 무엇이 달라지나

결정은 한곳에 남고, AI는 그것만 따릅니다

핵심은 하나입니다. 팀이 합의한 기획 내용을 한 문서에 모으고, 모든 사람의 AI가 그 문서만 보고 일하게 합니다. 이 가이드에서는 그 문서를 정본이라고 부릅니다. 정본을 두면 일하는 방식이 이렇게 바뀝니다.

기준이 서로 다르면 기획이 우선입니다

맨 위 기준

기획 문서 (정본)

기획자(PO/PM)가 쓰고 승인하는 정책과 화면 요구사항입니다. 여기에 없는 규칙은 디자인이나 코드에서 새로 만들지 않습니다.

기획을 따름

디자인 시안

디자이너가 Figma에서 '개발해도 된다'고 확정한 시안입니다.

  • 화면마다 정상 · 로딩 · 빈 화면 · 오류 · 권한 없음, 다섯 가지 상태를 모두 그립니다
  • 색과 크기는 이름 붙은 값(디자인 토큰)만 씁니다
기획을 따름

데이터 약속 (API 계약)

화면 개발자와 서버 개발자가 서로 기다리지 않고 동시에 만들 수 있게 미리 정해 둔 약속입니다.

  • 서버가 완성되기 전에도 가짜 응답으로 화면을 먼저 만듭니다
  • 정책이 걸린 항목의 의미를 바꿀 때는 기획자가, 기술 항목은 개발 리드가 승인합니다

실제 화면과 코드

세 기준을 모두 지킨 결과물만 합칩니다

시안과 데이터 약속이 서로 다르면 데이터 약속이 우선이고, 다른 점 자체를 질문으로 올립니다.
정책마다 번호를 붙입니다. 예를 들어 '부분 환불 수수료' 정책에 번호를 하나 붙이면, 같은 번호가 기획 문서, 데이터 약속, 테스트, 변경 기록에 함께 남습니다. 정책이 바뀌면 번호 검색 한 번으로 영향받는 곳이 나옵니다. 번호는 AI가 제안하고 기획자가 승인해야 확정됩니다. (번호 형식 예: POL-SETT-001)
이 절의 용어
정본
SSOT(Single Source of Truth). 여러 사본 중 기준이 되는 단 하나의 문서.
PO / PM
정책과 요구사항을 정하는 기획 담당. 이 가이드에서는 '기획자'라고 부른다.
API 계약
API는 화면과 서버가 데이터를 주고받는 창구. 계약은 그 창구로 무엇을 어떤 형식으로 주고받을지 미리 적어 둔 문서다.
디자인 토큰
색 · 글자 크기 · 간격 같은 디자인 값에 붙인 이름표. 코드와 시안이 같은 이름을 쓴다.
03 · 일의 흐름

일은 위에서 아래로, 질문은 아래에서 위로

기획자가 정하면 디자이너와 개발자가 만들고, 자동 검사와 리뷰어가 확인한 뒤 합칩니다. 만드는 사람이 모르는 것을 만나면 질문이 거꾸로 기획자에게 올라갑니다. 지시와 질문은 모두 GitHub에 기록으로 남으므로, 메신저 답변이 기준을 대신하지 않습니다.

04 · 사례로 따라가기

정책 하나가 고객에게 닿기까지

가상의 정책 "부분 환불 때 플랫폼 수수료를 어떻게 처리할까"가 결정부터 배포까지 움직이는 과정을 따라갑니다. 등장하는 번호는 모두 예시입니다.

  1. 1
    기획자가 정책을 정합니다AI 명령 /doc-update

    기획자가 AI에게 새 정책을 설명합니다. AI는 이 정책이 걸린 화면 2개와 데이터 약속 1곳을 찾아 "화면은 바뀌지 않는다"고 제안하고, 기획자가 확인합니다. 기획 문서가 고쳐지고, 담당 개발자 이름이 적힌 작업 지시서가 한 건 나옵니다. 화면이 바뀌는 건이었다면 이 사이에 디자이너가 시안을 확정합니다.

  2. 2
    개발자가 만들다가 빈칸 두 개를 만납니다AI 명령 /dev-screen

    첫째, 환불 버튼 문구가 기획 문서에 없습니다. 사소한 일이므로 개발자의 AI가 질문(142번)을 올리고, 적당한 문구로 가정해 계속 만듭니다. 둘째, 수수료를 몇 원 단위에서 반올림할지도 없습니다. 돈이 걸린 일이므로 질문(143번)을 올리고, 그 계산 부분만 막아 둔 채 다른 화면을 먼저 만듭니다. 질문이 올라가면 담당 기획자에게 알림이 자동으로 갑니다.

  3. 3
    기획자가 중요한 질문부터 답합니다답 = 기획 문서 수정

    기획자가 평소 할 일 목록에서 143번을 먼저 골라 반올림 규칙을 기획 문서에 적고 질문을 닫습니다. 개발자는 막아 둔 부분을 실제 계산으로 바꿉니다.

  4. 4
    결과물을 합칩니다자동 검사 + AI 대조 보고서

    142번 문구 질문은 아직 답이 없지만, 사소한 가정이라 합치는 데는 문제가 없습니다. 자동 검사는 테스트가 통과했는지, 막아 둔 부분이 남지 않았는지를 확인합니다. 리뷰어는 AI의 대조 보고서를 보고 승인합니다.

    가정 1건 → 합치기 가능멈춘 곳 0건테스트 통과
  5. 5
    배포 직전, 가정이 남아 있어 멈춥니다배포 관문

    배포를 시작하자 첫 단계에서 남은 가정을 세고, 142번이 남아 있어 배포가 멈춥니다. 주간 회의에서 이 건을 본 기획자가 문구를 기획 문서에 적어 질문을 닫고, 개발자가 가정했던 문구를 확정 문구로 바꿉니다.

    가정 1건 → 배포 중단정리 후 다시 배포
  6. 6
    배포하고 정리합니다다음 작업으로

    남은 가정이 없으니 배포가 통과합니다. AI가 작업 지시서를 '완료'로 바꿔 둡니다.

    가정 0건 → 배포 통과
실제 기록에는 정책 번호(POL-SETT-012), 지시서 번호(TASK-SETT-20261103-4f2a1), 코드 속 질문 표시([ASSUMPTION: Q-SETT-142]) 같은 형식이 남습니다. 이 형식은 AI가 맞춰 쓰므로 사람이 외우지 않아도 됩니다.
05 · 내 역할

내 역할에서 달라지는 것

옮겨 적기, 대조, 반복 검사는 AI와 자동 검사가 맡습니다. 사람은 아래 상황이 생겼을 때 정해진 곳에서 정해진 일만 하면 됩니다. 프로그램 사용법은 AI가 옆에서 안내합니다.

기획자 PO/PM

정하고 승인합니다

Git을 몰라도 됩니다. 고치는 일은 AI가 하고, 나는 바뀐 내용을 읽고 승인합니다. 기획 담당이 따로 없으면 결정 권한을 위임받은 사람이 이 역할을 맡습니다. 그 사람이 개발도 겸하면 자기가 짠 코드는 다른 사람이 승인합니다.

새 정책이나 요구사항이 생겼을 때

언제
새 기획, 정책 변경, 회의 결정이 생겼을 때
무엇을
AI에게 바뀐 내용을 말로 설명합니다. AI가 영향받는 화면과 화면이 바뀌는지를 알려 주면, 맞는지 보고 승인한 뒤 이 일을 맡을 사람을 정합니다.
어디서
Claude Code 앱에서 기획 저장소 폴더를 열고
끝 확인
AI가 올린 변경 요청을 GitHub 웹에서 읽고 승인합니다. 승인자가 나 혼자면 내용을 확인하고 직접 합칩니다(자기 요청은 자기가 승인할 수 없습니다).

언제

어디서

06 · 질문과 확인

모를 때 멈출지 계속할지 미리 정해 둡니다

모든 빈칸에서 멈추면 일이 밀리고, 아무 데서도 멈추지 않으면 AI의 짐작이 그대로 출시됩니다. 그래서 질문을 두 종류로 나누고, 어느 쪽이든 GitHub 질문 게시판에 남깁니다. 질문 번호는 게시판이 자동으로 붙이므로 AI가 지어내지 않습니다.

멈춤 질문 · BLOCKING

돈 · 권한 · 상태 변경 · 개인정보 · 결제

답이 오기 전에는 그 부분만 막아 두고, 같은 작업의 다른 부분을 먼저 만듭니다. 막아 둔 부분이 남아 있으면 결과물을 합칠 수 없습니다.

가정 질문 · ASSUMPTION

문구 · 정렬 · 사소한 화면 분기

가장 그럴듯한 가정으로 계속 만들고, 코드에 가정했다는 표시를 남깁니다. 합치는 것은 되지만, 표시가 하나라도 남아 있으면 배포는 안 됩니다.

확인은 두 단계로, 판단은 사람이

1단계 · 자동 검사

매번 같은 결과가 나오는 검사만 둡니다

  • 테스트코드 규칙 · 기능 테스트 통과
  • 질문막아 둔 부분 0건
  • 번호정책 번호 중복 · 미등록 0건
  • 선택켜 둔 팀만: 데이터 약속 검사 · 계산 검증
2단계 · AI 대조 보고서

AI는 보고하고, 사람이 판단합니다

  • 무엇을기획 문서 · 시안 · 데이터 약속과 결과물을 대조
  • 왜AI 판정은 할 때마다 조금씩 달라질 수 있어 자동으로 막지 않음
  • 결정리뷰어가 보고서를 보고 승인 · 반려
배포 관문

합치기는 열고, 배포는 닫습니다

  • 합치기가정 표시가 있어도 가능
  • 배포가정 표시가 0건이어야 시작
  • 정리답이 나오면 확정 근거로 바꾸고, 기각되면 가정한 코드를 되돌림
  • 관리열린 질문은 기획자의 할 일 목록과 주간 회의에서

AI 대조 보고서의 다섯 가지 판정

✅일치기획 · 시안 · 데이터 약속과 결과물이 모두 맞음
❌어긋남 · 빠짐기획에 있는 항목 · 계산 · 상태가 없거나 다름
⚠️임의로 만듦기획에 없는 규칙이 질문 없이 들어감
🟡가정하고 진행 중가정 질문을 남기고 먼저 만든 상태
❓기준이 아직 없음멈춤 질문의 답을 기다리는 상태
이 절의 용어
자동 검사 (CI)
Continuous Integration. 변경이 올라올 때마다 서버가 정해진 검사를 자동으로 돌리는 장치. 브랜드 CI와 다르다.
합치기 (병합)
검토가 끝난 변경을 팀 공용 원본에 넣는 일. 합쳐졌다고 바로 고객에게 나가는 것은 아니다.
배포 (릴리스)
실제 사용자에게 내보내는 일. 합친 것과 배포한 것은 다를 수 있다.
07 · 변경과 장애

화면이 바뀌는지만 가르고, 장애는 먼저 고칩니다

기획이 바뀔 때마다 AI가 화면이 바뀌는 일인지를 제안하고 기획자가 정합니다. 화면 구성이 바뀌면 디자이너를 거치고, 계산이나 조건만 바뀌면 디자인 단계를 건너뜁니다.

구분언제거치는 순서확인
화면이 바뀜새 화면, 화면 요소가 바뀔 때기획 → 작업 지시 → 디자인 → 구현 → 대조시안이 확정된 뒤 구현
화면은 그대로계산 · 조건 · 데이터 처리만 바뀔 때, 이미 배포된 오탈자기획 → 작업 지시 → 구현 → 대조 (디자인 생략)기획 문서 · 데이터 약속과 대조
긴급 수정 핫픽스운영 책임자가 장애로 선언한 건만먼저 고쳐 배포 → 나중에 기획 문서에 반영리뷰어 판단으로 먼저 배포합니다. 합친 사람이 '기획 문서에 반영할 일'을 질문 게시판에 올리고, 주간 회의에서 반영을 확인합니다
개발 중 발견한 사소한 문구는 긴급 수정이 아니라 가정 질문으로, 이미 배포된 오탈자는 일반 작업 지시로 처리합니다. 긴급 수정은 운영 장애에만 씁니다.

개발 저장소는 정해 둔 버전의 기획 문서만 받아 씁니다. 기획 문서가 바뀌면 그 버전을 올리는 변경 요청을 따로 올립니다.

화면은 두 갈래로 만듭니다

화면 시안 파일 수십 개를 손으로 관리하는 대신, 관리자 화면은 표준 틀로, 고객 화면은 디자이너의 Figma 시안으로 기준을 잡습니다.

관리자 화면 · ADMN-*

백오피스 · 어드민

  • 목록과 팝업, 상세 입력, 통계 대시보드, 탭 복합의 네 가지 틀 중 하나를 고릅니다
  • 기획 문서에 적힌 검색 조건 · 표 항목 · 팝업을 틀에 끼웁니다
  • 맞는 틀이 없으면 틀 추가를 질문하고, 가장 가까운 틀로 진행합니다
고객 화면 · USER-*

서비스 · 브랜드 화면

  • 디자이너가 기획 문서를 바탕으로 Figma 시안을 만들고 디자인 토큰에 연결합니다
  • AI는 확정 시안을 Figma에서 직접 읽고 기존 부품을 다시 씁니다(연결 설정은 선택 부록)
  • AI가 화면 배치를 임의로 바꾸지 않습니다

AI 명령 다섯 가지

사람이 AI에게 내리는 표준 명령입니다. 원문은 이 저장소의 skills/ 폴더에 있고, 설치할 때 각 저장소에 복사합니다.

/dev-screen

개발자 · 리뷰어

기준과 대조하기

기획 문서 · 시안 · 데이터 약속과 결과물을 대조해 다섯 가지 판정 보고서를 냅니다. 파일은 고치지 않습니다.

/spec-check

10 · 용어

자주 나오는 말 8개

규칙이나 수치가 이 페이지와 다르면 핵심 규약이 맞습니다.

정본 · 기획 문서SSOT

팀이 합의한 기준을 모은 단 하나의 문서. 정본 > 데이터 약속 > 시안 순으로 따르고, 셋이 다르면 위가 맞습니다.

정책 번호POL-*

정책마다 붙는 영구 번호. 기획 문서 · 데이터 약속 · 테스트 · 변경 기록에 같은 번호를 남깁니다.

질문 번호Q-ID

질문 게시판이 붙인 번호로 만든 질문 이름(예: Q-SETT-142). AI가 지어내지 않습니다.

가정 진행ASSUMPTION

사소한 빈칸을 가정으로 채우고 계속하는 것. 합치기는 되지만 가정 표시가 남아 있으면 배포가 안 됩니다.

화면 요약본Digest

화면 하나에 필요한 항목 · 상태 · 팝업 · 계산식만 뽑은 요약. AI는 기획 문서 전체 대신 이것을 읽어 비용을 아낍니다.

작업 지시서TASK

지시 한 건에 파일 하나. 화면이 바뀌는지와 담당자가 적혀 있고, AI는 내 이름이 적힌 것만 맡습니다.

두 단계 확인CI + AI 보고서

자동 검사는 매번 같은 결과가 나오는 것만 막고, AI 판정은 보고서로 남겨 리뷰어가 정합니다.

팀 설정 파일agentic-env.yaml

설정 질문 12개의 답을 적어 둔 파일. 업무 영역, 담당자, 켤 선택 기능은 여기서 바꿉니다.
