01 · Why

여러 사람이 각자 AI를 쓰면 정본이 흩어집니다

AI를 잘 쓰는 개인이 늘수록, 정본을 안 읽거나 빈틈을 AI가 추론해 채운 코드도 함께 늘어납니다. 이 규약은 네 가지 문제를 막기 위해 만들었습니다.

01

정본 이탈

AI가 빈틈을 임의로 추론해 정본과 다른 상태값 · 로직 · 코드를 만듭니다.

02

도메인 간 충돌

여러 PO/PM과 FE/BE가 도메인을 나눠 병렬로 일할 때 식별자 · 계산식 · API 스키마가 어긋납니다.

03

화면 파편화

정적 HTML 프로토타입을 손으로 관리하지 않으면서도 백오피스와 유저 화면의 통일성을 지켜야 합니다.

04

수동 검수 병목

사람이 정본과 코드를 눈으로 대조하는 대신, 로컬 스킬과 중앙 CI가 먼저 걸러야 합니다.

02 · Hierarchical SSOT

정본은 평면이 아니라 계층입니다

기획의 비즈니스 정책이 최상위 원천이고, 디자인과 인터페이스 계약은 거기서 파생됩니다. 최상위 정본에 없는 상태값이나 로직은 디자인 · 코드에서 새로 만들 수 없습니다.

ROOT

최상위 비즈니스 정본 (Root Logic SSOT)

PO/PM이 작성 · 승인하는 정책서와 화면 요구사항. spec-repo/docs/specs/

VISUAL

시각 정본

UIX 디자이너가 Figma로 확정한 시안과 디자인 시스템 (Ready for Dev)

  • 화면 상태 매트릭스(정상 · 로딩 · 빈 화면 · 오류 · 권한 없음 + 도메인 상태)
  • Semantic 토큰만 사용, 미바인딩 값 0개
CODE

인터페이스 정본

FE · BE가 기다리지 않고 병렬로 만들기 위해 먼저 확정하는 API 계약

  • contracts/openapi.yaml + Mock, 해설서 00_domain_contracts.md
  • POL 필드 의미 변경은 PO/PM, 기술 필드는 FE · BE 리드 승인

실제 화면과 코드

정본 · 시안 · 계약을 모두 지킨 구현만 병합합니다

정책 추적 ID POL-SETT-001 하나를 정책서 · 색인 · API description · 테스트 주석 · 커밋 메시지에 똑같이 남깁니다. 정책이 바뀌면 이 ID 검색 한 번으로 영향 범위가 나옵니다. 번호는 대장(_registry.yaml)에 예약해 쓰고, AI는 제안만 합니다.
03 · Two Repositories

정본 저장소와 개발 저장소를 나눕니다

기획 자산과 소스 코드를 섞지 않아 AI가 옛 초안을 참조하는 일을 막고, 승인 권한도 직군별로 나눕니다.

  • src/FE · BE 프로덕션 코드

04 · Workflow

정의 → 지시 → 구현 → 대조, 그리고 되돌아오는 질문

05 · Questions & Gates

멈출 질문과 진행할 질문을 나눕니다

모든 질문에서 멈추면 병목이 되고, 아무 질문에서도 멈추지 않으면 정본이 흩어집니다. 질문은 GitHub Issue로 올리고, Issue 번호가 그대로 질문 ID가 됩니다(예: Q-SETT-142).

BLOCKING

금액 · 권한 · 상태 전이 · 개인정보 · PG

해당 분기는 스텁([BLOCKED: Q-ID])으로 막고 같은 지시서의 다른 작업으로 넘어갑니다. 답이 오기 전에는 main에 병합하지 않습니다.

ASSUMPTION

문구 · 정렬 · 사소한 UI 분기

가장 합리적인 가정으로 진행하고 코드에 [ASSUMPTION: Q-ID]를 남깁니다. 정본에 반영돼 Issue가 completed로 닫힐 때까지 릴리스는 기다립니다.

게이트는 두 층, ASSUMPTION은 두 단계

1층 · CI 필수 체크

결과가 늘 같은 검사만

  • 계약OpenAPI 계약 테스트
  • 계산도메인 계산기 정답 대조
  • DB임시 DB 테스트 · 코드 스타일
  • 질문ASSUMPTION · BLOCKED 주석 상태
2층 · AI 리포트

판단은 리뷰어가

  • PR/spec-check 결과를 코멘트로
  • 이유AI 판정은 실행마다 달라질 수 있음
  • 결정리뷰어가 리포트를 보고 반려 · 승인
ASSUMPTION 주석

main은 열고, 릴리스는 닫는다

  • main미해결 · completed 허용
  • mainIssue 없음(Q-PENDING) 차단
  • 릴리스completed만 허용
  • 정리기각은 코드 제거, 중복은 원본 ID로

/spec-check 판정 5종

✅일치정본 · 시안 · 계약과 코드가 모두 맞음
❌위반 · 누락정본에 있는 필드 · 계산식 · 상태가 없거나 다름
⚠️임의 구현정본에 없는 규칙이 질문 없이 들어감
🟡가정 진행ASSUMPTION 주석으로 선진행 중
❓정본/시안 미정의Blocking 질문으로 멈춘 상태
06 · Fast-Track

모든 변경을 같은 무게로 돌리지 않습니다

AI가 변경 등급을 제안하고 PO/PM이 확정합니다. 화면 명세 표가 바뀌면 L2로 제안됐어도 L1으로 올립니다.

등급언제경로게이트
L1 Full Track신규 화면, UI와 로직이 함께 바뀔 때정의 → 지시서 → Figma → 구현 → 대조모든 게이트
L2 Logic & PatchUI 변경 없이 수식 · 조건 · DB 로직만, 배포된 오탈자정의 → 개발 지시서 → 구현 → 대조 (UIX 생략)UI 검수 생략, 정본 · 계약 검증 필수
L3 Hotfix운영 책임자가 장애로 선언한 건만긴급 수정 · 배포 → 정본 사후 동기화리뷰어 예외 승인으로 선배포. 영업일 3일(기본값) 안에 정본을 동기화하지 않으면 담당자 재알림 → 리드 에스컬레이션, 개발 병합은 막지 않음
개발 중 발견한 사소한 문구 · UI 분기는 L3가 아니라 ASSUMPTION 경로로, 이미 배포된 오탈자는 L2로 처리합니다. L3는 운영 장애 선조치에만 씁니다.
07 · Two UI Tracks

화면은 성격에 따라 두 트랙으로

정적 HTML 프로토타입을 수십 개 관리하는 대신, 백오피스는 표준 골격으로, 유저 화면은 디자이너의 Figma 시안으로 시각 기준을 잡습니다.

TRACK A

백오피스 · 어드민 ADMN-*

  • 표준 골격 4종: List-Modal · Detail-Form · Stats-Dashboard · Tabs-Complex
  • 정본 화면 명세의 필터 · 컬럼 · 모달을 골격에 결합
  • 맞는 골격이 없으면 골격 추가 질문을 올리고 가장 가까운 골격으로 진행
TRACK B

유저 프론트 · 브랜드 USER-*

  • PRD로 Figma 초안을 만들고 디자인 시스템 토큰에 바인딩
  • Figma MCP로 확정 시안을 읽고, Code Connect(또는 컴포넌트 매핑표)로 기존 컴포넌트 재사용
  • AI가 레이아웃을 임의로 바꾸지 않음

10 · Adoption

도입 순서

먼저 온보딩 질문지로 팀별 설정값(SLA · 담당자 · 라벨 · 웹훅 등 48개)을 정하고, 시범 도메인 하나로 한 바퀴 돌린 뒤 CI에 고정합니다.

STEP 1

설정값 정하기

질문지에 답해 agentic-env.yaml 작성

STEP 2

저장소 · 스킬

명세서를 AI에 읽혀 2-Repo와 5대 스킬 생성

STEP 3

공통 계약

/doc-rule로 API 계약 · UI 골격 고정

STEP 4

시범 1사이클 → CI

요구사항 1건으로 전 과정 검증 후 check.sh를 필수 체크로

프로젝트 유형시작 방법먼저 답할 질문
신규 구축2-Repo 생성 → /doc-init으로 초안 정본화 → 계약 수립 → 구현저장소 · 담당자 · 식별자 · 디자인 시스템
전면 리뉴얼구버전 코드 역분석 → 의심 로직은 레거시 질문(도메인당 상한) → 리뉴얼 요건 반영라벨 · 담당자 · 게이트
운영 · 고도화이번에 고칠 도메인만 정본화 → 그 도메인부터 게이트 적용브랜치 전략 · 릴리스 판별 · CI
작업 지시와 질문의 정답 기록은 Git과 spec-repo Issue 하나입니다. 사내 업무 플랫폼이나 Google Workspace를 연결해도 알림 · 미러 용도로만 씁니다.
11 · Glossary

꼭 알아야 할 용어 8개

전체 용어 사전은 명세서 0절에 있습니다. 규칙 · 수치가 이 페이지와 다르면 명세서가 맞습니다.

계층형 정본Hierarchical SSOT
비즈니스 정책을 최상위로 두고 시각 정본(Figma)과 인터페이스 정본(API 계약)이 파생되는 구조.
정책 추적 IDPOL-*
정책마다 붙는 영구 번호. 정책서 · 색인 · API · 테스트 · 커밋에 같은 ID를 남겨 영향 범위를 찾는다.
질문 IDQ-ID
spec-repo Issue 번호로 만든 질문 식별자(Q-SETT-142). AI가 지어내지 않는다.
가정 진행ASSUMPTION
사소한 공백을 가정으로 채우고 진행한 상태. main 병합은 되지만 completed 종결 전에는 릴리스가 안 된다.
화면 요약본Digest
화면 하나에 필요한 필드 · 상태 · 모달 · 수식만 뽑은 요약. AI는 정본 전체 대신 이것을 읽는다.
변경 등급Fast-Track L1~L3
신규 · 대규모(L1), UI 무변동 로직 · 패치(L2), 운영 장애 선조치(L3)로 나눈 경로.
게이트 2층CI + AI Report
