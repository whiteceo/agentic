01 · 한눈에 보기

사람은 정의하고 결정합니다

PO/PM, 디자이너, 개발자가 각자 AI를 써도 결과물이 하나의 기준 문서에 맞물리도록 하는 규약입니다. 전달, 대조, 반복 검사는 AI와 자동 검사가 맡습니다. 처음 보는 분은 6절(내 역할)까지만 읽어도 충분합니다.

기준 문서는 하나

비즈니스 정책이 맨 위에 있고, API 계약과 디자인 시안은 정책을 따릅니다.

반복 작업은 AI가

정본 작성부터 구현, 대조까지 표준 스킬 5종으로 처리합니다.

검수는 2단계

자동 검사가 먼저 막고, AI 리포트는 리뷰어가 보고 판단합니다.

팀마다 정할 것은 12개

나머지 규칙은 공통입니다. 저장소에 설치하는 것은 규약 1개와 GitHub 자동화 2개입니다.

02 · 왜 필요한가

각자 AI를 쓰면 기준이 흩어집니다

AI는 문서에 빈칸이 있으면 그럴듯한 답을 추측해 채웁니다. 실제로 일을 나눠 개발자마다 각자 AI를 돌리고 병합해 보니, 같은 문서를 기준으로 했는데도 코드가 충돌하고 서로 맞지 않는 부분이 생겼습니다. 이 규약은 그 경험에서 출발했고, 문제는 다음 네 가지로 나타납니다.

⇢

기획과 다른 구현

AI가 기획서에 없는 할인 조건이나 상태값을 추측으로 만들고, 기획자는 출시 직전에야 알게 됩니다.

⇄

병합 때 드러나는 충돌 · 불일치

각자 AI로 만든 코드를 합치면 같은 문서를 봤는데도 충돌이 나고, 같은 '정산 금액'을 화면 개발자와 서버 개발자가 다르게 계산합니다. 여러 기획자가 동시에 일할 때도 같은 일이 생깁니다.

▦

화면마다 다른 모양

AI로 화면을 빨리 만들수록 버튼과 배치가 화면마다 조금씩 달라집니다.

◎

사람 눈에 기댄 검수

기획서와 결과물을 사람이 전부 눈으로 대조하면 검수가 늘 병목이 됩니다.

03 · 무엇이 달라지나

기준은 한곳에 두고, AI는 그것만 읽습니다

핵심은 단순합니다. 팀이 합의한 정책과 요구사항을 하나의 기준 문서에 모으고, 모든 사람의 AI가 그 문서를 보고 일하게 합니다. 이 가이드에서는 그 문서를 정본이라고 부릅니다.

상황지금도입 후
정책 결정회의록, 메신저, 기획서에 흩어짐PO/PM이 AI에게 설명하면 AI가 정본 수정안을 올리고, PO/PM이 검토해 승인
구현 중 빈칸메신저로 묻거나 AI가 추측해 채움GitHub에 질문으로 남김. 금액 · 권한처럼 중요한 건 그 부분만 멈추고, 문구처럼 사소한 건 가정하고 진행
화면 제작화면마다 모양을 새로 정함관리자 화면은 표준 골격 4종 중에서 고르고, 사용자 화면은 디자이너가 확정한 시안을 따름
검수사람이 기획서와 결과물을 눈으로 대조자동 검사가 먼저 거르고, 리뷰어는 AI 대조 리포트를 보고 판단
배포 직전미확정 사항이 섞여 나갈 수 있음가정으로 진행한 항목이 하나라도 남으면 배포가 멈춤
정책 변경고칠 곳을 사람이 일일이 찾음정책 번호로 영향받는 화면과 코드를 한 번에 검색

세 기준이 어긋나면 위가 맞습니다

셋이 서로 다르면 위가 맞고, 어긋난 사실 자체를 질문으로 올립니다.

1순위

비즈니스 정본

PO/PM이 작성하고 승인하는 정책서와 화면 요구사항입니다. 정본에 없는 상태값이나 로직은 디자인이나 코드에서 새로 만들 수 없습니다.

2순위

API 계약

화면 개발자와 서버 개발자가 서로 기다리지 않고 동시에 개발할 수 있도록, 주고받을 데이터를 미리 정해 둔 문서입니다.

  • 서버가 완성되기 전에는 Mock(가짜 응답)으로 화면을 먼저 만듭니다
  • 정책과 연결된 항목의 의미는 PO/PM이, 기술 항목은 FE · BE 리드가 승인합니다
3순위

디자인 시안

디자이너가 Figma에서 개발 가능(Ready for Dev)으로 확정한 시안과 디자인 시스템입니다.

  • 화면마다 정상 · 로딩 · 빈 화면 · 오류 · 권한 없음 상태를 모두 그립니다
  • 색과 크기는 이름이 붙은 디자인 토큰만 씁니다

실제 화면과 코드

세 기준을 모두 지킨 구현만 병합합니다

정책마다 추적 번호를 붙입니다. 예를 들어 '부분 환불 수수료' 정책에 POL-SETT-012 같은 번호를 붙이면, 같은 번호가 정본, API 계약, 테스트, 커밋 기록에 함께 남습니다. 나중에 정책이 바뀌면 이 번호 하나로 영향 범위를 찾을 수 있습니다. 번호는 AI가 제안하고, 정본이 승인될 때 확정됩니다.
이 절의 용어
정본
SSOT(Single Source of Truth). 여러 사본 가운데 기준이 되는 단 하나의 문서.
PO / PM
정책과 요구사항을 정하는 기획 담당.
API 계약
API는 화면과 서버가 데이터를 주고받는 창구. 계약은 무엇을 어떤 형식으로 주고받을지 미리 적어 둔 문서다.
FE / BE
FE는 사용자가 보는 화면, BE는 서버와 데이터 처리를 맡는 개발자.

05 · 사례로 따라가기

정책 하나가 배포되기까지

가상의 정책 "부분 환불 시 플랫폼 수수료 처리"를 따라가 봅니다. 번호는 모두 예시입니다.

  1. 1
    PO/PM이 정책을 정합니다/doc-update

    PO/PM이 AI에게 새 정책을 설명합니다. AI는 이 정책이 걸린 화면 2개와 API 1개를 찾아내고 "UI 변경 없음"을 제안합니다. PO/PM이 확인하면 정본과 API 계약이 개정되고, 담당 개발자가 지정된 작업 지시서가 발행됩니다. UI가 바뀌는 건이었다면 이 단계에서 디자이너가 시안을 확정합니다.

  2. 2
    개발자가 구현 중 빈칸 두 곳을 만납니다/dev-screen

    환불 버튼 문구가 정본에 없습니다. 사소한 문제라서 AI가 질문 #142를 올리고, 적당한 문구를 가정해 작업을 이어 갑니다. 수수료 반올림 단위도 정해져 있지 않습니다. 금액이 걸린 문제라서 Blocking(멈추고 묻는) 질문 #143을 올리고, 해당 계산만 막아 둔 채 다른 화면을 먼저 만듭니다. 질문이 올라가면 담당 PO/PM에게 자동으로 알림이 갑니다.

  3. 3
    PO/PM이 Blocking 질문부터 답합니다답변 = 정본 수정

    PO/PM은 백로그에서 #143을 먼저 골라 반올림 규칙을 정본에 반영하고 질문을 닫습니다. 개발자는 막아 두었던 부분을 실제 계산 로직으로 바꿉니다.

  4. 4
    main에 병합합니다자동 검사 + AI 리포트

    #142에는 아직 답이 없지만, 가정으로 진행한 사소한 항목이라 병합은 가능합니다. 자동 검사는 테스트를 통과했는지, 막아 둔 코드가 남지 않았는지 확인합니다. 리뷰어는 AI 대조 리포트를 검토해 승인합니다.

    가정 1건 → 병합 가능Blocking 0건테스트 통과
  5. 5
    배포 직전, 남은 가정 때문에 멈춥니다배포 관문

    배포를 시작하면 첫 단계에서 남은 가정을 확인합니다. #142가 남아 있어 배포가 멈춥니다. 주간 회의에서 이를 확인한 PO/PM이 문구를 정본에 반영해 질문을 닫고, 개발자는 가정했던 문구를 확정 문구로 바꿉니다.

    가정 1건 → 배포 중단정리 후 다시 실행
  6. 6
    배포하고 마무리합니다다음 작업으로

    남은 가정이 없으므로 배포가 통과합니다. 병합 뒤에는 AI가 작업 지시서를 완료 상태로 바꿉니다.

    가정 0건 → 배포 통과
실제 기록에는 POL-SETT-012(정책 번호), TASK-SETT-20261103-4f2a1(작업 지시서), [ASSUMPTION: Q-SETT-142](코드에 남는 가정 표시) 같은 형식이 쓰입니다. 형식은 AI가 맞춰 쓰므로 사람이 외울 필요는 없습니다.

07 · 질문과 검수

멈출 질문과 진행할 질문을 나눕니다

모든 질문에서 멈추면 일이 밀리고, 아무 데서도 멈추지 않으면 AI의 추측이 그대로 출시됩니다. 질문은 어느 쪽이든 GitHub Issue로 올립니다.

BLOCKING · 멈추고 묻기

금액 · 권한 · 상태 전이 · 개인정보 · 결제

답이 나올 때까지 해당 부분만 막아 두고, 같은 작업의 다른 부분을 먼저 진행합니다. 막아 둔 코드가 남아 있으면 main에 병합할 수 없습니다.

ASSUMPTION · 가정하고 진행

문구 · 정렬 · 사소한 UI 분기

가장 합리적인 가정으로 진행하고 코드에 가정 표시를 남깁니다. 병합은 가능하지만, 표시가 하나라도 남아 있으면 배포할 수 없습니다.

검수는 두 단계, 배포 전 남은 가정은 0건

1단계 · 자동 검사(CI)

매번 결과가 같은 검사만

  • 테스트코드 스타일 · 단위 · 기능 테스트
  • 질문막아 둔 코드 0건
  • 번호정책 번호 중복 · 미등록 0건
  • 선택계약 테스트 · 계산 검증(켠 팀만)
2단계 · AI 리포트

판단은 리뷰어가

  • PR/spec-check 결과를 PR 코멘트로 남김
  • 이유AI 판정은 실행할 때마다 달라질 수 있음
  • 결정리뷰어가 보고 승인 또는 반려
배포 관문

병합은 허용, 배포는 차단

  • 병합가정 표시가 있어도 가능
  • 배포첫 단계에서 가정 표시 0건 확인
  • 정리답이 나오면 가정 표시를 확정 내용으로 바꾸고, 기각되면 코드를 되돌림
  • 관리열린 질문은 PM 백로그와 주간 회의에서

AI 리포트의 판정 다섯 가지

✅일치정본 · 시안 · API 계약과 코드가 모두 맞음
❌위반 · 누락정본에 있는 항목 · 계산식 · 상태가 없거나 다름
⚠️임의 구현정본에 없는 규칙이 질문 없이 들어감
🟡가정 진행가정 질문을 남기고 먼저 진행 중
❓정본 미정의Blocking 질문의 답을 기다리는 중
이 절의 용어
CI
Continuous Integration. 변경이 올라올 때마다 서버가 정해진 검사를 자동으로 돌리는 장치. 브랜드 CI와 다르다.
main
팀 전체가 기준으로 쓰는 공용 원본 코드.
병합
검토가 끝난 변경을 main에 합치는 일. 병합했다고 바로 사용자에게 나가지는 않는다.
배포
실제 사용자에게 내보내는 일(릴리스).
08 · 변경과 핫픽스

화면이 바뀌는지부터 정하고, 장애는 먼저 고칩니다

정책이 바뀌면 AI가 UI 변경 여부를 제안하고 PO/PM이 작업 지시서에 확정합니다. 화면 명세가 바뀌면 "UI 변경 있음"입니다.

구분언제경로관문
UI 변경 있음신규 화면, 화면 요소 변경정의 → 작업 지시 → Figma → 구현 → 대조시안 확정 후 구현
UI 변경 없음계산 · 조건 · 데이터 로직만 변경, 배포된 오탈자정의 → 작업 지시 → 구현 → 대조 (디자인 생략)정본 · API 계약과 대조
핫픽스운영 책임자가 장애로 선언한 건만긴급 수정 · 배포 → 정본 사후 동기화리뷰어 판단으로 먼저 배포합니다. 병합한 사람이 hotfix-sync Issue를 올려 PM 백로그에 넣고, 주간 회의에서 동기화를 확인합니다
개발 중 발견한 사소한 문구는 핫픽스가 아니라 가정 진행으로, 이미 배포된 오탈자는 일반 작업 지시로 처리합니다. 핫픽스는 운영 장애에만 씁니다.

화면은 두 트랙으로 만듭니다

정적 HTML 프로토타입 수십 개를 관리하는 대신, 관리자 화면은 표준 골격으로, 사용자 화면은 디자이너의 Figma 시안으로 기준을 잡습니다.

TRACK A · ADMN-*

관리자 화면 (백오피스)

  • 표준 골격 4종: 목록+모달(List-Modal) · 상세 입력(Detail-Form) · 통계(Stats-Dashboard) · 탭 복합(Tabs-Complex)
  • 정본에 적힌 필터 · 컬럼 · 모달을 골격에 끼웁니다
  • 맞는 골격이 없으면 골격 추가를 질문하고, 가장 가까운 골격으로 진행합니다
TRACK B · USER-*

사용자 화면 (서비스 · 브랜드)

  • 디자이너가 정본을 바탕으로 Figma 시안을 만들고 디자인 토큰에 연결합니다
  • AI는 Figma 연동(MCP)으로 확정 시안을 읽고 기존 컴포넌트를 재사용합니다(설정은 선택 부록)
  • AI가 레이아웃을 임의로 바꾸지 않습니다

질문 번호Q-ID

정본 저장소 Issue 번호로 만든 질문 이름(예: Q-SETT-142). AI가 지어내지 않습니다.

가정 진행ASSUMPTION

사소한 빈칸을 가정으로 채우고 진행하는 상태. 병합은 되지만 가정 표시가 남아 있으면 배포되지 않습니다.

화면 요약본Digest

화면 하나에 필요한 필드 · 상태 · 모달 · 계산식만 뽑은 요약. AI는 정본 전체 대신 이것을 읽어 토큰(사용량)을 아낍니다.

작업 지시서TASK

지시 1건에 파일 1개. UI 변경 여부와 담당자가 적혀 있고, AI는 내 계정이 적힌 지시서만 맡습니다.

2단계 검수CI + AI 리포트

자동 검사는 결과가 늘 같은 검사만 막고, AI 판정은 PR 리포트로 남겨 리뷰어가 정합니다.

팀 설정 파일agentic-env.yaml

설정 질문 12개의 답을 적어 둔 파일. 도메인, 담당자, 켤 선택 기능은 여기서 바꿉니다.
