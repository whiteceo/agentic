PO/PM · 디자이너 · 개발자가 각자 AI를 써도 하나의 정본(기준 문서)에 맞물리게 하는 규약입니다. 사람은 정의하고 결정하고, 전달 · 대조 · 반복 검사는 스킬과 CI가 맡습니다.

01 · 왜 필요한가

각자 AI를 쓰면 정본이 흩어집니다

AI를 잘 쓰는 개인이 늘수록, 정본을 안 읽거나 빈틈을 AI가 추론해 채운 코드도 같이 늘어납니다. 이 규약은 네 가지 문제를 막습니다.

⇢

정본 이탈

AI가 빈틈을 임의로 추론해 정본과 다른 상태값 · 로직을 만듭니다.

⇄

도메인 충돌

여러 PO/PM과 FE/BE(화면 · 서버 개발자)가 병렬로 일할 때 식별자 · 계산식 · API(데이터 주고받는 창구)가 어긋납니다.

▦

화면 파편화

프로토타입을 손으로 관리하지 않으면서 화면 통일성을 지켜야 합니다.

05 · 질문과 게이트

멈출 질문과 진행할 질문을 나눕니다

모든 질문에서 멈추면 병목이 되고, 아무 데서도 멈추지 않으면 정본이 흩어집니다. 질문은 GitHub Issue로 올리고 Issue 번호가 그대로 질문 ID가 됩니다(예: Q-SETT-142).

BLOCKING

금액 · 권한 · 상태 전이 · 개인정보 · PG

해당 분기는 스텁(임시로 막아 둔 코드, [BLOCKED: Q-ID])으로 막고 같은 지시서의 다른 작업으로 넘어갑니다. 답이 오기 전에는 main(공용 원본)에 병합하지 않습니다.

ASSUMPTION

문구 · 정렬 · 사소한 UI 분기

가장 합리적인 가정으로 진행하고 [ASSUMPTION: Q-ID]를 남깁니다. Issue가 completed(정본 반영 완료)로 닫히기 전에는 릴리스(사용자에게 배포)하지 않습니다.

게이트는 두 층, ASSUMPTION은 두 단계

1층 · CI 필수 체크

결과가 늘 같은 검사만

  • 계약OpenAPI 계약 테스트
  • 계산도메인 계산기 정답 대조
  • DB임시 DB 테스트 · 코드 스타일
  • 질문ASSUMPTION · BLOCKED 주석 상태
2층 · AI 리포트

판단은 리뷰어가

  • PR/spec-check 결과를 코멘트로
  • 이유AI 판정은 실행마다 달라질 수 있음
  • 결정리뷰어가 보고 반려 · 승인
ASSUMPTION 주석

main은 열고, 릴리스는 닫는다

  • main미해결 · completed 허용
  • mainIssue 없음(Q-PENDING) 차단
  • 릴리스completed만 허용
  • 정리기각은 코드 제거, 중복은 원본 ID로

06 · 사례로 따라가기

정책 하나가 릴리스까지 가는 길

가상의 정책 "부분 환불 시 플랫폼 수수료 처리"(POL-SETT-012)가 지시에서 릴리스까지 어떻게 움직이는지 따라갑니다. 등장하는 번호는 모두 예시입니다.

  1. 1
    PO/PM이 정책을 정의합니다/doc-update · 번호 대장

    AI가 POL-SETT-012에 걸린 화면 2개와 API 1개를 찾아 L2(UI 변경 없음)를 제안하고, PO/PM이 확정합니다. 정본 · 계산기 · 계약이 개정되고 지시서 TASK-SETT-20261103-4f2a1이 나옵니다. 머지 후 Actions가 인덱스를 갱신합니다. UI가 바뀌는 L1이었다면 이 사이에 디자이너가 Figma 시안을 Ready for Dev로 확정하고 정본에 URL을 등록합니다.

  2. 2
    개발자가 구현하다 빈틈 두 개를 만납니다/dev-screen

    환불 버튼 문구는 정본에 없습니다. 사소하므로 Issue #142를 올리고(담당자 지정 · 알림은 Actions(자동 실행 작업)가 보냄) [ASSUMPTION: Q-SETT-142]를 달고 진행합니다. 수수료 반올림 단위도 없습니다. 금액이므로 Issue #143(Blocking)을 올리고, 그 분기만 [BLOCKED: Q-SETT-143] 스텁으로 막은 채 다른 화면을 만듭니다.

  3. 3
    PO/PM이 Blocking 질문부터 답합니다정본 수정 → completed

    PO/PM이 반올림 규칙을 정본에 적고 #143을 completed로 닫습니다. Actions가 질문 아카이브 파일을 만듭니다. 개발자는 스텁을 실제 로직과 @policy POL-SETT-012로 바꿉니다.

  4. 4
    main 병합CI 1층 + AI 리포트 2층

    #142는 아직 답이 없지만 main 병합은 됩니다. CI는 계약 · 계산기 테스트를 돌리고, /spec-check 리포트는 PR 코멘트로 남아 리뷰어가 확인합니다.

    Q-SETT-142 · 미해결 → main 허용BLOCKED 0건계약 · 계산기 통과
  5. 5
    릴리스 직전, 가정이 남아 있으면 멈춥니다릴리스 게이트

    릴리스 태그(버전 이름표)를 찍자 배포 작업이 릴리스 게이트를 기다리고, #142가 아직 열려 있어 배포가 멈춥니다. PO/PM이 문구를 정본에 반영하고 #142를 completed로 닫습니다.

    Q-SETT-142 · 미해결 → 릴리스 차단정본 반영 후 재시도
  6. 6
    릴리스, 그리고 정리다음 /dev-screen

    모든 가정이 completed라 릴리스가 통과합니다. 다음 작업 때 AI가 [ASSUMPTION: Q-SETT-142]를 @policy POL-SETT-012로 바꾸고, 지시서는 PR 머지로 DONE이 됩니다.

    전부 completed → 릴리스 통과

07 · 변경 등급

모든 변경을 같은 무게로 돌리지 않습니다

AI가 변경 등급을 제안하고 PO/PM이 확정합니다. 화면 명세 표가 바뀌면 L2로 제안됐어도 L1으로 올립니다.

등급언제경로게이트
L1 Full Track신규 화면, UI와 로직이 함께 바뀔 때정의 → 지시서 → Figma → 구현 → 대조모든 게이트
L2 Logic & PatchUI 변경 없이 수식 · 조건 · DB 로직만, 배포된 오탈자정의 → 개발 지시서 → 구현 → 대조 (UIX 생략)UI 검수 생략, 정본 · 계약 검증 필수
L3 Hotfix운영 책임자가 장애로 선언한 건만긴급 수정 · 배포 → 정본 사후 동기화리뷰어 예외 승인으로 선배포. 영업일 3일(기본값) 안에 정본을 동기화하지 않으면 담당자 재알림 → 리드 에스컬레이션(상급자 보고). 개발 병합은 막지 않음
