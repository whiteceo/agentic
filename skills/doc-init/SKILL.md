# /doc-init — 정본 처음 만들기

규칙은 `AGENTS.md`(핵심 규약)를 따른다. 결과는 PR 하나이며, 도메인 담당자가 병합해야 확정된다.

## 1. 출발점 고르기
사용자에게 묻는다: ① 기획서 · 정책 문서가 있다 ② 운영 중인 코드만 있다 ③ 둘 다 있다 ④ 아무것도 없다.
- ①: 기획서를 아래 형식으로 옮긴다.
- ②: 라우트 · 컨트롤러 · 뷰 · DB 마이그레이션에서 화면과 규칙을 뽑는다. 하드코딩 · 죽은 코드 · 모순이 의심되면 정본으로 확정하지 않고 `legacy-question` Issue로 올린다(금액 · 권한 등 Blocking 범주면 `blocking-question`도). 도메인당 한 번에 20건까지, 넘치면 목록을 묶은 Issue 1건.
- ③: 기획서를 기준으로 쓰고 코드와 다른 곳을 `legacy-question`으로 올린다.
- ④ **인터뷰**: 서비스 목적과 사용자 → 도메인 목록 → 도메인별 화면 → 화면별 입력 · 상태 · 버튼 → 금액 · 권한 · 상태 전이 규칙 순으로 하나씩 묻는다. 답하지 못한 항목은 지어내지 않고 Blocking 질문으로 표시한다. spec-repo가 아직 없으면 초안을 작업 폴더 `draft/`에 두고, 저장소가 생기면 PR과 Issue로 올린다.

## 2. 정본 형식 (`docs/specs/<번호>_<이름>.md`)
- 맨 위 `## 문서 개정 이력` 표: `v1.0.0 | YYYY-MM-DD | 담당자 | 초기 정본`.
- `[A]` 유저 화면(`USER-*`) ↔ 백오피스(`ADMN-*`) 짝 표.
- `[B]` 화면 명세 표(열 순서는 설치서 5-2): 화면코드 · 화면명 · Figma URL(없으면 `-`) · Ref POL · 화면 상태.
- `[C]` 정책 본문: 정책마다 `<a id="pol-<도메인>-<번호>"></a>` 다음 줄에 `### [POL-<도메인>-<번호>] <정책명>`. 정책 본문은 여기에만 쓴다.
- 화면 코드는 `ADMN-<도메인>-<NNN>` · `USER-<도메인>-<NNN>`. POL 번호는 `_registry.yaml`에 `active`로 넣어 같은 PR에 담는다. 병합되면 확정이고, 반려되면 PR과 함께 사라진다.

## 3. 요약본
- 화면마다 `docs/digest/<화면코드>.md`: 필드 · 상태 · 버튼 · 모달 · 연결된 POL과 핵심 수식만. 정본 전체의 일부만 읽어도 구현할 수 있게 짧게 쓴다.
- 색인(`canon_index.md`)은 만들지 않는다. `sync-spec.sh`가 로컬에서 만든다.
