## 1. 목적과 범위

- **목적**: 큰 회사가 여러 에이전틱 도메인을 묶어 관제하고(엔터프라이즈 · 서비스화), 작은 회사는 칸을 건너뛰어 가볍게 쓰게 한다.
- **범위**: 관리 계층의 칸, 칸마다 역할 · 권한, 정책 상속과 실효 정책 계산, 긴급 정지 범위, 관측 요약, 도메인 붙이기 · 옮기기 · 떼기, 테넌트 사이 격리의 원칙.
- **범위 밖**: 업무 결정(하위 도메인 · 경계 맥락 · 정본)은 업무 계층(DDD)의 일이다. 요금 · 계약 · SSO 연동 방식 같은 상품 일은 상품 설계에서 정한다.

## 2. 두 축

| 축 | 칸 | 묻는 것 | 결정자 |
| :--- | :--- | :--- | :--- |
| 관리 계층 | 테넌트 → 조직 → 팀 → 에이전틱 도메인 | 누가 비용을 내나, 신원 · 정책을 누가 관리하나, 무엇을 모아 보나 | 칸마다의 관리 책임자 |
| 업무 계층(DDD) | 에이전틱 도메인 → 하위 도메인 → 경계 맥락 | 무엇을 만드나, 규칙의 뜻은 무엇인가 | 도메인 결정자(PO) |

- 두 축은 에이전틱 도메인 한 칸에서만 만난다. 도메인은 관리 계층의 한 칸에 **소속**되고, 그 안의 업무는 업무 계층이 정한다.
- 관리 칸은 업무 결정을 가져가지 않는다(개념 아키텍처 10-3). 위험 수용 서명은 도메인 결정자 자리에 그대로 있다.

## 3. 칸과 역할

| 칸 | 둘 수 있는 수 | 관리 책임자 | 정할 수 있는 것 | 정할 수 없는 것 |
| :--- | :--- | :--- | :--- | :--- |
| 테넌트(고객사) | 회사마다 하나 | 테넌트 관리자 + 보안 책임자 | 신원 체계 · 비밀값 · 데이터 등급 · 허용 모델과 도구의 상한 · 비용 상한 · 보관 기간 기본값 · 도메인 규격 판의 허용 범위 | 업무 결정, 위험 수용 서명 |
| 조직(사업부) | 0개 이상 | 조직 관리자 | 위 칸보다 엄한 정책, 관문 수준의 바닥, 비용 배분 | 위 칸보다 느슨한 정책, 업무 결정 |
| 팀 | 0개 이상 | 팀 관리자(보통 PM) | 위 칸보다 엄한 정책, 관문 수준의 바닥, 도메인 붙이기 신청 | 위와 같음 |
| 에이전틱 도메인 | 팀(또는 위 칸)마다 여럿 | 도메인 결정자(PO) · 도메인 책임자 | 관문 수준(바닥 이상), 하위 도메인 · 정본 · 역할표, 다시 켜기 | 위 칸 정책보다 느슨하게 하기 |

- 쓰지 않는 칸은 건너뛴다. 가장 작은 꼴은 테넌트 → 에이전틱 도메인이다.
- 사람은 이름이 아니라 역할로 적고, 사람과 역할의 대응은 신원 제공자에 둔다.
- 한 사람이 여러 칸의 책임자를 맡을 수 있다. 다만 도메인 결정자가 같은 도메인의 바닥을 정한 위 칸 책임자를 겸하면, 바닥을 정한 기록에 그 사실을 적는다.

## 4. 정책 상속과 실효 정책

### 4-1. 정책의 종류와 합치는 규칙

| 정책 | 예 | 합치는 규칙 |
| :--- | :--- | :--- |
| 허용 목록 | 쓸 수 있는 모델 · 도구 | 교집합(위 칸이 허용한 것 안에서만 더 줄일 수 있음) |
| 차단 목록 | 막는 데이터 등급 · 막는 도구 | 합집합(어느 칸이든 막으면 막힘) |
| 상한 값 | 실행당 · 칸당 비용, 호출 수 | 가장 작은 값 |
| 바닥 값 | 관문 수준의 바닥 | 가장 큰 값(가장 엄한 것) |
| 단일 값 | 신원 체계 | 테넌트만 정한다(아래 칸은 바꾸지 못함) |
| 보관 기간 | 기록 · 원기록의 보관 기간 | 바닥(가장 긴 법정 보존 기한, 가장 큰 값)과 천장(파기 의무, 가장 작은 값) 두 값으로 합친다. 테넌트는 기본값을 두고, 도메인은 법령 근거를 적어 바닥을 올린다. 바닥이 천장보다 크면 결정적 검사가 막고 도메인 결정자에게 간다(법 > 계약 > PO 결정 순서, DDD 대조 11-14) |

- 아래 칸이 위 칸보다 느슨한 값을 적으면 그 줄은 무시되고, 정책 원본이 판 올림 PR에서 경고한다(결정적 검사).
- 이 규칙은 클라우드의 조직 정책 상속과 같은 모양이다(신뢰 3·학습 지식).

### 4-2. 실효 정책 계산

1. 도메인에서 테넌트까지 위로 올라가며 칸 정책을 모은다.
2. 4-1의 규칙으로 합친다. 결과에는 줄마다 **어느 칸이 정했는지**(출처 칸)와 판 번호를 붙인다.
3. 정책 원본이 도메인마다 실효 정책 묶음을 만들고, 정책 집행점이 당겨 간다(관제 평면 설계 2절).
4. 어느 칸에서든 실효 정책 보기를 연다. "이 호출은 왜 막혔나"와 "왜 수준 1로 못 내리나"는 출처 칸으로 답한다.

## 5. 긴급 정지 범위

| 누른 칸 | 멈추는 것 | 다시 켜는 사람 |
| :--- | :--- | :--- |
| 테넌트 | 테넌트 안 모든 에이전트 | 각 도메인 책임자(테넌트가 정지를 푼 뒤 도메인마다) |
| 조직 · 팀 | 그 칸 아래 모든 도메인의 에이전트 | 같음 |
| 도메인 | 그 도메인의 에이전트 | 도메인 책임자 |
| 에이전트 · 신원 | 그 에이전트 하나 | 도메인 책임자 |

- 위 칸의 정지가 풀려도 도메인은 저절로 다시 켜지지 않는다. 도메인 책임자가 다시 켜고 기록을 남긴다(DDD 대조 11-14).
- 정지는 정책 집행점이 당겨 가는 정지 목록과, 짧게 사는 자격의 갱신 중단 두 길로 걸린다(관제 평면 설계 3절).

## 6. 관측 요약

- 원기록(실행 증명 · 집행 기록)은 도메인 단위로 지우지 않고 남긴다. 위 칸은 **요약만** 본다: 칸 아래의 비용, 실패 · 정지 수, 판정 뒤집힘 수, 관문 수준 분포, 열린 질문 수.
- 요약은 보기용이다. 사람 표본 검토와 관문 수준 판단은 원기록에서 뽑는다.
- 감시 에이전트는 칸마다 둘 수 있고, 자기 칸 아래의 요약과 원기록만 읽는다.

## 7. 흐름

1. **도메인 붙이기**: 팀 관리자가 신청 → 도메인 규격 적합성 시험(결정적) 통과 → 등록부에 한 줄(소속 칸, 결정자, 작업판, 규격 판) → 정책 원본이 실효 정책 묶음을 만듦 → 처음 관문 수준 3.
2. **도메인 옮기기(팀 · 조직이 바뀜)**: 등록부의 소속 칸만 바꾼다. 업무 계층(하위 도메인 · 정본 · 역할표)은 그대로다. 실효 정책이 바뀌므로, 새 실효 정책으로 관문 수준 바닥이 올라가면 도메인 수준도 따라 올라간다. 내려가지는 않는다(내리는 것은 도메인 결정자가 9-8대로).
   - 오른 수준은 그 뒤에 여는 판정부터 건다. 이미 지난 수준으로 통과한 판정은 그대로 둔다(소급하지 않음). 진행 중인 판정을 새 수준으로 다시 받게 할지는 도메인 결정자가 정한다.
   - 수준이 바뀐 것을 도메인 역할표와 기록에 한 줄로 남긴다(칸 이름, 바닥을 정한 책임자, 바뀐 시각). 도메인 결정자에게 알린다.
3. **도메인 떼기**: 그 도메인이 주인인 공개 계약을 넘겨받을 도메인을 먼저 정한다 → 에이전트 정지 → 신원 폐기 → 등록부에 '닫힘'. 원기록은 보존 기간만큼 둔다.
4. **도메인 간 변경**: 걸린 도메인들을 덮는 가장 낮은 칸(LCA)이 변경을 열고 정책을 합친다. 업무 해석 · 선택은 걸린 도메인의 결정자가 근거 순서대로 정한다(개념 아키텍처 10-3).
5. **칸 정책 바꾸기**: 칸 관리자가 정책 원본에 PR → 결정적 검사(느슨해지는 줄 경고) → 칸 관리자 승인 → 판 올림 → 아래 도메인의 실효 정책 묶음 갱신. 관문 수준 바닥을 올리는 PR에는 이유와 재검토 조건을 적는다(핵심규약 9-8과 같은 꼴).

## 8. 테넌트 사이 격리 (원칙만)

- 신원 · 정책 · 원기록 · 등록부는 테넌트마다 나뉜다. 한 테넌트의 에이전트는 다른 테넌트의 작업판 · 계약을 읽지 못한다.
- 테넌트 사이 공개 계약이 필요하면 '타사 에이전트'처럼 정책 집행점에서 만난다.
- 격리를 어떻게 구현할지(저장소 · 계정 · 키 분리)는 상품 설계에서 정한다.

## 9. 시범 기간의 모습

- 지금은 테넌트 하나, 칸 없음, 에이전틱 도메인 하나다. 관리 계층 문서는 미리 정해 두되, 등록부 · 칸 정책은 두 번째 도메인이 붙을 때 켠다(개념 아키텍처 10-2).
- 그 전까지 테넌트 정책은 규약 원본 저장소(이 저장소)의 공통 정책, 도메인 정책은 `agentic-env.yaml`이다.

## 10. 남은 결정

1. **(DDD 대조)** 4-1 합치는 규칙, 7-2 도메인 옮기기 때 바닥이 올라가면 수준도 따라 올라가는 규칙.
2. **(상품 설계)** SSO 연동, 감사 내보내기, 데이터 보관 지역, 테넌트 격리 구현.
3. **(두 번째 도메인 때)** 등록부 형식과 칸 정책 파일 형식.
