## 1. 실행 연결: GitHub Actions에서 에이전트를 한 번씩 돌린다

- 에이전트 실행 = **GitHub Actions 잡 하나에서 Claude Code를 헤드리스로 한 번 실행**(`claude -p` 또는 Anthropic의 Claude Code GitHub Action) (신뢰 3·학습 지식). 잡이 끝나면 에이전트도 끝난다. 상주 서버 · 큐는 없다(설계 1절).
- 실행마다 저장소를 새로 체크아웃하고, 스킬 원문(`.claude/skills/`)과 `AGENTS.md`만 쓴다. 이전 실행의 대화 · 캐시를 넘기지 않는다(독립 조건이 구조로 지켜짐).
- 같은 대상에 실행이 겹치지 않게 워크플로마다 `concurrency`(대상별 그룹, 진행 중 실행 취소 안 함)를 둔다 (신뢰 3·학습 지식).

### 워크플로 넷 (에이전트 역할과 1:1)

| 워크플로 | 저장소 · 트리거 | 역할 · 스킬 | 결과 |
| :--- | :--- | :--- | :--- |
| `agent-lead.yml` | spec-repo · `push: main`에서 `docs/specs/**`가 바뀜 | 총괄 · `/doc-update --tasks-from <병합 커밋>` | TASK PR 1개(후보 TASK 여러 건 + 배정 후보). 기존 `/doc-update`의 TASK 발행 단계를 그대로 쓴다. 새 스킬을 만들지 않는다 |
| `agent-write.yml` | app-repo · `repository_dispatch`(spec-repo에서 TASK가 병합됐고 `assignee`에 작성 에이전트 계정이 있음 / 그 TASK가 막혔던 Q-ID Issue가 닫힘) | 작성 · `/dev-screen` | 코드 PR(첫 줄 `Task: <TASK id>`), 막히면 질문 Issue |
| `agent-judge.yml` | app-repo · `pull_request: opened, synchronize` / spec-repo · `docs/specs/**`를 바꾼 PR | 판정 · `/spec-check`(app) · 정본 원문 대조(spec, `/spec-check --spec`) · 구현 전 일관성(spec-repo `docs/changes/**`를 바꾼 총괄 TASK PR) · 변경 단위 취합(아래) | 기록 줄이 붙은 리포트 코멘트(커밋마다 새 코멘트 1개. 앞 판정 기록은 지우지 않는다) |
| `merge-bot.yml` | 두 저장소 · `workflow_run`(agent-judge 완료) · `pull_request_review: submitted` | 병합 봇(AI 아님, 셸 스크립트) | 아래 2절 조건이 모두 참이면 병합, TASK `DONE` PR |

- `repository_dispatch`는 spec-repo의 작은 연결 단계(TASK 병합 · Issue 닫힘을 보고 app-repo에 알림)가 보낸다. 별도 워크플로를 만들지 않고 `agent-lead.yml`과 `assign-issue.yml`에 한 단계씩 붙인다.
- 정본 원문 대조는 `/spec-check`의 모드 하나로 둔다(`--spec`: 바뀐 정본 절 ↔ 그 절이 인용한 상위 원문). 스킬 수는 5종 그대로다.
- **실패**: 잡이 실패하거나 에이전트가 끝을 못 내면 대상(TASK PR · 코드 PR · TASK Issue)에 `agent-failed` 라벨과 실행 링크 한 줄. 재시도 워크플로는 두지 않는다(설계 5절).
- **넓히기 단계 정하기**: `agent-lead.yml`이 TASK PR을 올릴 때 셸 스크립트가 TASK 수와 걸린 POL의 `risk: A`로 단계를 정해 라벨(`scale:single` · `scale:multi` · `scale:multi-risk`)을 단다. AI가 정하지 않는다. 이 라벨이 구현 전 일관성 · 취합 판정을 켤지, 판정에 다른 모델을 쓸지를 정한다.
- **변경 단위 취합의 깨어남**: TASK의 `status`가 바뀌는 spec-repo PR이 병합되면, 셸 스크립트가 같은 TASK PR(같은 정본 변경)에서 나온 TASK가 모두 닫혔는지 보고, 그렇고 `scale:multi*`이면 `agent-judge.yml`을 취합 모드로 부른다.
- **고침 반복**: 판정 리포트에 ❌가 있으면 `agent-write.yml`을 같은 PR에 다시 부르고 PR에 `fix-1` · `fix-2` 라벨을 단다. `fix-2` 뒤에도 ❌면 `agent-failed`로 멈춘다.
- **화면 겹침**: `agent-write.yml`은 시작할 때 `screen_ids`가 겹치는 열린 코드 PR이 있으면 TASK에 `agent-waiting` 라벨만 달고 끝난다. 다시 돌리는 것은 사람(PM)이 라벨을 떼고 재실행한다.

## 2. 관문 수준을 기계로 거는 방법 (새 장치 대신 GitHub 기본 기능)

| 수준 | 코드 PR · 정본 PR | 릴리스 |
| :---: | :--- | :--- |
| 3 | 병합 봇은 아무것도 하지 않는다. 사람이 판정하고 병합한다(지금과 같음) | 배포 작업의 Environment에 필수 검토자(운영 책임자) (신뢰 3·학습 지식) |
| 2 | 리포트가 ✅뿐 + 작성자가 아닌 사람의 승인 리뷰 1개 → 병합 봇이 병합 | 같음(필수 검토자가 리포트 묶음을 보고 승인) |
| 1 | 리포트가 ✅뿐 → 병합 봇이 병합. 사람은 사후 revert PR | 필수 검토자 없음. 배포 노트에 기록만 |

- **병합 봇의 조건(모두 참)**: ① 그 PR의 수준이 1 또는 2 ② 최신 커밋의 리포트 기록 줄이 있고 판정 수행자 ≠ PR 작성자 ③ 리포트 항목이 모두 ✅ ④ 자동 관문(`check`) 통과 ⑤ 풀리지 않은 리뷰 대화 0개 ⑥ (수준 2면) 작성자가 아닌 사람의 승인 1개. 조건 판단은 셸 스크립트로 하고 AI를 부르지 않는다(자동 관문처럼 결정적).
- **반박 = 리뷰 대화**: 리포트 항목에 반박하려면 그 PR에 리뷰 코멘트를 단다. 브랜치 보호의 "대화 해결 필수"를 켜 두면 풀리지 않은 반박이 있는 동안 누구도 병합하지 못한다 (신뢰 3·학습 지식). 반박 전용 장치를 만들지 않는다. 반박 대화는 반박을 단 사람이나 책임자(리뷰어 · PM)만 해결로 닫는다. 작성자(사람 · 작성 에이전트)는 닫지 않는다.
- **PR의 수준 정하기**: 그 PR이 건드린 POL(코드 `@policy` · 커밋 `Ref:` · 정본 앵커) 중 대장(`_registry.yaml`)에 `risk: A`가 하나라도 있으면 `risk_a` 값, 아니면 `default` 값. 리포트가 "A 결과를 바꿀 수 있음"을 적었는데 대장에 표시가 없으면 병합 봇은 수준 2로 올려 다루고, 리뷰어가 확정한다.
- **작성자 병합 금지**: 수준 1 · 2 관문이 있는 저장소에서는 main 병합 권한을 병합 봇과 리뷰어(사람)에게만 두고, 작성 에이전트 계정에는 주지 않는다. 사람 작성자가 자기 PR을 병합하지 못하게 거는 방법은 GitHub 저장소 규칙으로 가능한지 미확인이다(시범에서 실측). 안 되면 핵심규약 5-5의 약속으로 두고 병합 봇의 조건 ②가 그 PR을 거른다.

## 3. 계정 · 토큰 (최소 권한, 역할마다 따로)

| 계정 | 형태 | 권한 | 쓰는 워크플로 |
| :--- | :--- | :--- | :--- |
| 작성 에이전트 | GitHub App `<org>-agent-writer` | 두 저장소 contents · pull requests 쓰기, issues 쓰기(질문 Issue). main 병합 권한 없음 | agent-lead, agent-write |
| 판정 에이전트 | GitHub App `<org>-agent-judge` | contents 읽기, pull requests 코멘트만 | agent-judge |
| 병합 봇 | GitHub App `<org>-merge-bot` | contents 쓰기(병합), pull requests 쓰기 | merge-bot |
| 모델 키 | 저장소 Secrets 하나(`ANTHROPIC_API_KEY` 등, 이름은 설정 질문) | — | agent-* |

- 머신 사용자 계정보다 GitHub App을 권한다. 저장소 단위로 권한을 좁히고 토큰이 짧게 산다 (신뢰 3·학습 지식).
- **근거(분리)**: 작성 · 판정 · 병합(운영 적용)을 다른 주체가 하는 것은 국내 금융 IT 규정과도 맞는다. 전자금융감독규정 제29조와 같은 규정 시행세칙 제2조의7(2 · 3 · 6 · 7호: 기록, 제3자 검증, 시험 뒤 책임자 승인, 담당자 이외의 자에 의한 운영 적용), 정보시스템 감리기준 제10조의2③(수행자 분리)(신뢰 5, DDD 방법론 쪽이 원문 확인, 11-14). 금융 도메인이 아니어도 같은 분리를 기본으로 둔다.
- 총괄 에이전트는 작성 에이전트 App을 같이 쓴다(둘 다 '작성'이고 병합 권한이 없다). 판정 에이전트와는 반드시 다른 App이다.
- 판정 에이전트 실행에 넘기는 입력: PR diff · 해당 정본 절 · 계약 operation · 정본이 인용한 상위 원문(핵심규약 7절). 작성 PR의 본문 중 "작업 메모"류는 넘기지 않는다.
- 같은 모델을 쓰게 되면(키가 하나뿐인 팀) 기록 줄에 `same_model=yes`.

## 4. 실행 기록 한 줄 (형식)

결과물(PR 본문 첫 줄 아래, 리포트 머리)에 사람용 한 줄과 기계용 주석 한 줄을 둔다.

```markdown
> 실행: 판정 에이전트 · claude-<모델> · spec-check@<스킬 커밋 7자> · 워크플로 agent-judge@<커밋 7자> · 대조 <head 7자> · 결과 ✅4 ❌0 · 토큰 12.3k/2.1k · 같은 모델 아님
<!-- agentic-run: role=judge model=<모델 ID> skill=spec-check@<sha> workflow=agent-judge@<sha> result=pass:4,fail:0 base=<sha> head=<sha> tokens_in=12345 tokens_out=2100 same_model=no run=<Actions 실행 URL> -->
```

- **실행 증명과 서명(DDD 대조 11-14)**: 시범 기간 실행 증명은 Actions 실행 링크와, 저장소(PR 코멘트)에 남긴 실행 요약으로 한다. 요약에는 커밋 · 워크플로 판 · 결과, AI가 판정했으면 모델 · 지침 판을 적는다. Actions 기록은 보존 기한이 지나면 사라지므로(기본 90일, 신뢰 3·학습 지식) 링크만으로는 근거 기록이 서지 않는다. 서명(위험 수용) · 책임자 이름(승인 · 병합) 자리는 링크로 대신하지 않고, 사람 이름이 붙은 리뷰 승인이나 기록 줄로 남긴다. 서명된 출처 증명(산출물 증명 등)은 정책 집행점과 함께 넣는다(기능 · 요금제 미확인).
- 기계용 줄은 나중에 관측성 · 비용 집계(선택 부록 6절)가 그대로 긁어 가게 하려는 것이다. 지금은 모으는 장치를 만들지 않는다. 항목 이름은 OpenTelemetry 생성형 AI 속성과 대응시킬 수 있게 둔다(신뢰 3·학습 지식).
- 릴리스 태그 노트에는 그때의 `gates` 값, 이번 릴리스에 든 PR들의 리포트 링크, 위 기계용 줄을 모은 표를 넣는다(배포 작업이 만든다).

## 5. 설정 (`agentic-env.yaml` 추가분)

```yaml
risk_a_categories: [금액, 세무·법적 의무, 되돌릴 수 없는 결과, 개인정보, 권한]   # DDD L2. 하위 도메인이 더할 수 있음
agents:
  enabled: false                 # 9단계에서 켬. false면 지금처럼 사람만 한다
  writer_app: <org>-agent-writer
  judge_app: <org>-agent-judge
  merge_app: <org>-merge-bot
  model_secret: ANTHROPIC_API_KEY
gates:                           # 3 사람 / 2 AI + 사람 승인 / 1 AI 통과, 사후 되돌림
  task_split: {default: 3}        # 총괄 에이전트의 TASK PR
  spec_merge: {default: 3, risk_a: 3}
  code_merge: {default: 3, risk_a: 3}
  release: 3
  target: {task_split: 2, spec_merge: 1, code_merge: 1, risk_a: 2, release: 2}   # 내릴 때의 목표값(DDD 기본값)
  review_after_days: 30
  max_tokens_per_run: 200000     # 실행당 토큰 상한(12-Factor). 넘으면 멈추고 agent-failed. 값은 팀이 정함, 자리표시자
# 긴급 정지(시범 기간): agents.enabled를 false로 바꾸는 PR이 도메인 단위 정지다. 다시 켜기(true)는 하위 도메인 담당자 승인 PR로만 한다.
```

- **처음 값은 모두 3**이다(설계 8절: 판정 에이전트부터, 지금과 같은 효력으로 시작). `target`은 DDD가 제안한 기본값(등급 A · 릴리스 = 2, 나머지 = 1)이고, PO가 9-8대로 PR을 열어 관문별로 내린다. 처음부터 목표값으로 깔지 않는 이유는 내릴 근거(뒤집힘 0건 기록)가 아직 없어서다.
- `_registry.yaml` POL 항목에 `risk: A`를 쓸 수 있게 한다: `POL-SETT-005: {status: active, title: <정책명>, risk: A}`.
- 설정 질문 추가: 13 위험 등급 A 범주(더할 것) · 14 에이전트를 켤지와 App · 모델 키 이름 · 15 관문 수준을 3에서 시작할지(권장) 바로 목표값으로 둘지.

## 6. 설치 9단계 "에이전트 켜기" (8단계 시범 뒤)

| 순서 | 할 일 | 누가 | 끝 확인 |
| :---: | :--- | :--- | :--- |
| 9-1 | GitHub App 셋 만들고 두 저장소에 설치, 모델 키를 Secrets에 | 사람 | App 셋이 두 저장소 설치 목록에 있음 |
| 9-2 | 워크플로 넷과 연결 단계 넣기, `agents.enabled: true` | AI → 세팅 담당 리뷰 | 테스트 PR에 판정 리포트(기록 줄 포함)가 달림 |
| 9-3 | 브랜치 보호: 대화 해결 필수, main 병합 권한에서 작성 에이전트 App 제외, 릴리스 Environment 필수 검토자 | 사람 | 반박 코멘트가 풀리지 않은 테스트 PR이 병합되지 않음 |
| 9-4 | 시범: 정본 PR 1건 → 총괄 TASK PR → 작성 → 판정 → 사람 병합(수준 3) | 전원 | 각 결과물에 실행 기록 줄 |

## 7. 그림자 판정 (시범 1단계의 운영 방식)

판정 에이전트를 처음 들일 때는 관문 효력 없이 **그림자로** 돌린다. 지금 길의 판정(사람이든 기존 판정자든, 그 관문의 지금 수준 그대로)은 그대로 두고, 판정 에이전트가 같은 대상을 따로 판정해 둘을 견준다. 도입 순서 1단계(`에이전틱_도메인_설계.md` 10절)의 시범 모습이다.

1. **효력 없음**: 그림자 판정은 병합 · 확정 · 다른 결정의 근거로 쓰지 않는다. 리포트 머리에 `그림자`를 단다.
2. **독립**: 판정 에이전트는 지금 길의 판정 기록을 입력으로 받지 않는다. 기준(정본 · 판정 기준 문서 · 상위 원문)과 대상만 읽는다. 지금 길의 판정이 끝난 뒤에야 둘을 견준다.
3. **실행 방식(시범)**: 워크플로가 깔리기 전에는, 작성 세션 · 지금 길의 판정 세션과 다른 새 Claude 세션 하나를 열어 판정 지침 · 기준 · 대상만 넘기고 판정 리포트를 받는다. 실행 요약(4절 형식, 워크플로 칸 대신 '수동 세션')을 저장소에 남기고, 모델 · 지침 판을 반드시 적는다.
4. **견주기**: 항목마다 지금 길의 판정과 그림자 판정을 나란히 적는다. 갈린 항목은 반대 검토로 어느 쪽이 맞는지 가린다. 반대 검토 수행자는 작성자 · 두 판정자와 다르고 기록을 남기며, 최종은 그 관문의 서명자가 정한다(DDD L2. AI도 독립 조건과 기록을 갖추면 수행할 수 있고, 사람으로만 묶으려면 도메인 역할표에서 정한다). 견주기 기록에는 그것을 닫은 책임자 이름을 적는다.
5. **재는 것**: 일치율, 갈린 항목 가운데 그림자 쪽이 맞았던 수(지금 길이 놓친 것), 그림자 쪽이 틀린 수(잘못된 ❌ · 놓친 ❌), 판정 하나당 토큰 · 시간. 이 기록이 관문 수준을 지금 수준에서 내릴지 정하는 근거(핵심규약 9-8)다. 위 칸이 정한 수준 바닥(`개념_아키텍처.md` 10-3)보다는 내리지 못한다.
6. **끝내기**: 정한 건수 또는 기간을 채우면 결과를 견주기 기록과 함께 묶어 하위 도메인 결정자에게 올린다. 지금 수준에서 내릴지는 그 사람이 정한다.

### 7-1. 그림자 판정 세션에 넘기는 지침 (꼴과 순서만)

판정 기준은 그 도메인의 판정 기준 문서를 그대로 쓴다. 이 지침은 리포트 꼴과 실행 순서만 정하고 기준을 더하지 않는다(기준을 더하면 견줄 수 없다).

- **세션 열기**: 항목마다 새 세션 하나. 작성 · 지금 길 판정을 한 세션과 다르고, 그 프로젝트의 기억 · 대화 · 공유 폴더를 읽지 않는 자리(빈 작업 폴더)에서 연다. 작업 폴더에는 고정 커밋에서 꺼낸 '읽는 것'만 둔다. 저장소 전체를 넘기지 않는다.
- **세션에 주는 글(본문)**:
  ```
  너는 그림자 판정자다. 이 판정은 효력이 없고 기록으로만 쓴다.
  1. 이 폴더의 파일만 읽는다. 다른 파일 · 저장소 · 웹 · 기억을 보지 않는다.
  2. 판정 기준은 <판정 기준 문서>다. 기준에 없는 잣대를 더하지 않는다.
  3. 대상 <영역 파일>의 <항목>을 기준의 항목마다 판정한다(기준 문서의 판정 값을 그대로 쓴다).
  4. 원문이 모호 · 충돌 · 침묵하면 판정하지 말고 '해석 필요'와 근거만 적는다.
  5. 리포트는 아래 꼴로만 쓴다.
  ```
- **리포트 꼴**:
  ```markdown
  # 그림자 판정: <항목> @<대상 커밋>
  | 기준 항목 | 판정 | 근거(파일 · 절 · 줄) |
  | :--- | :--- | :--- |
  해석 필요: <없으면 '없음'>
  > 실행: 그림자 판정 · <모델> · 지침 실행_연결 7-1@<커밋> · 수동 세션 · 대조 <대상 커밋> · 결과 <요약> · 토큰 <in/out> · 시간 <분>
  ```
- **실행 순서**: ① 고정 커밋에서 읽는 것을 꺼내 빈 폴더에 둔다 ② 새 세션을 열고 본문을 넘긴다 ③ 리포트를 받아 그대로(고치지 않고) 정해진 자리에 커밋한다 ④ 세션을 닫는다. 리포트를 고치거나 다시 돌려 고르지 않는다(한 번 판정만 쓴다).

## 8. 확인이 필요한 곳
