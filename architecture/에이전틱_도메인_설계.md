## 1. 목적과 범위

- **목적**: 운영 규약(사람과 AI가 같은 흐름을 따름) 위에, 에이전트가 스스로 일을 받아 돌고 관문에서 멈추는 실행 구조를 얹는다.
- **범위**: 에이전틱 도메인 하나의 안쪽. 도메인 사이와 관제 평면은 `개념_아키텍처.md`가 다룬다.
- **지킬 원칙(white 11-01)**: ① 하나의 파이프라인으로 충돌을 막고 토큰을 아낀다 ② 거시 흐름 먼저 ③ 예외마다 장치를 덧대지 않고 사람 판단(PM 백로그 · 주간 회의)에 맡긴다.
- **범위 밖**: white님 작업 환경의 Claude 세션끼리 주고받는 중계(voice-instruct `docs/route/PROTOCOL.md` 17절)는 이 체계 밖의 운영 도구다.

## 2. 작업판 원리

**에이전틱 도메인마다 작업판은 하나다. 에이전트끼리 대화하지 않는다.** 에이전트는 작업판의 상태(질문 · 변경 요청 · 작업 지시서)가 바뀔 때 깨어나 자기 몫만 하고, 결과를 작업판 상태로 남긴 뒤 끝난다. 별도 큐 · 데이터베이스 · 에이전트 간 메시지 채널을 두지 않는다.

- **작업판의 조건 셋**: ① 상태(열림 · 확정 · 닫힘)와 기록이 남는다 ② 상태가 바뀌면 신호를 낸다 ③ 확정(병합)에 권한을 걸 수 있다. 기준 구현은 GitHub(Issue · PR · 저장소 파일)이고, 이 문서의 'GitHub'는 작업판을 뜻한다.
- **이유**: 충돌(상태가 한 곳에만 있어 두 에이전트가 같은 일을 다르게 기억할 수 없음), 토큰(대화를 이어받지 않고 핵심규약 7절 읽기 범위만 읽음), 독립(작성 대화를 판정 입력으로 받지 않는 조건이 구조로 지켜짐).

## 3. 흐름

```
사람: 결정 ─▶ 정본 PR ─[판정: 원문 대조]─▶ 병합 ─▶ 총괄: TASK 후보 ─[판정: 구현 전 일관성]─[사람(PM) 확인]─▶ TASK 발행
                                                        │
              ┌──────── 질문 Issue ◀── 막힘(Blocking) ──┤
              │  사람 답 = 정본 PR 병합 → Issue 닫힘 ──▶ 재개
              ▼                                         ▼
          PM 백로그                          작성 에이전트: 구현 → 코드 PR
                                                        │
                                  자동 관문 check ──────┤
                                  판정 에이전트(다른 세션) ── 리포트 + 실행 증명
                                                        │
                                  수준 3 사람 / 2 AI + 사람 승인 / 1 병합 봇
                                                        ▼
                                                 병합 → TASK DONE
변경 단위 취합: 한 정본 변경의 TASK가 모두 닫힘(DONE · 취소 · 보류) ─▶ [판정: 취합] ─▶ 빠짐은 보충 TASK 후보 또는 질문
릴리스: check --release ─▶ [판정: 릴리스(취합 결과 근거)] ─▶ 배포(사람 실행)
```

칸과 순서는 핵심규약 2절 그대로다. 새로 생기는 것은 누가 그 칸을 실행하느냐뿐이다.

## 4. 사안에 따라 넓히기 (기본은 싱글)

검사와 에이전트 수는 상시 최대로 돌리지 않고, 사안의 크기와 위험에 따라 넓힌다(white 11-14). Anthropic 연구 시스템도 일의 난이도에 따라 하위 에이전트 수를 정한다(신뢰 4).

| 단계 | 조건(기계로 판단) | 도는 것 |
| :---: | :--- | :--- |
| 싱글 | 정본 변경 1건에서 TASK 1건, 위험 등급 A 없음 | 작성 1 + PR 판정 1회. 구현 전 검사 · 취합 판정은 건너뜀 |
| 멀티 | TASK 2건 이상 | 싱글 + 구현 전 일관성 검사 + 변경 단위 취합 판정 |
| 멀티 + 위험 | 위험 등급 A가 하나라도 걸림 | 멀티 + 판정 에이전트는 작성과 다른 모델 · 지침 판, 관문 수준 하한 2 |

- 단계는 총괄의 TASK PR 내용(TASK 수 · 걸린 POL의 `risk: A`)으로 정한다. 같은 사안이면 늘 같은 단계다.
- TASK를 일부러 1건으로 묶어 검사를 피하는지는 TASK PR 관문(사람 확인)에서 본다.
- 단계는 위로만 바뀐다. 도중에 TASK가 늘거나 등급 A가 붙으면 올리고, 지난 검사는 다시 돌린다.

## 5. 에이전트 역할 (다섯, 더 늘리지 않는다)

| 역할 | 깨어나는 때 | 하는 일 | 못 하는 일 | DDD 역할 |
| :--- | :--- | :--- | :--- | :--- |
| **총괄 에이전트** | 정본 PR 병합, 막힌 Q-ID Issue가 닫힘 | 변경을 TASK 후보로 쪼개고 배정 후보를 붙여 TASK PR로 올림 | 판정, 병합, 정본 결정, 정본에 없는 규칙 만들기, 작성 대화를 판정 쪽에 넘기기 | 작성(후보) |
| **작성 에이전트** | TASK `assignee`에 자기 계정, 막혔던 Q-ID Issue가 닫힘 | `/dev-screen`(코드) · `/doc-update` 초안(정본, 사람이 지시했을 때) → PR | 병합, 판정, 정본 결정, 남의 TASK | 작성 |
| **판정 에이전트** | PR 열림 · 새 커밋(총괄 TASK PR 포함), 한 정본 변경의 TASK가 모두 닫힘, 릴리스 판정 요청 | 6절의 검사 넷 → 실행 증명 붙은 리포트 | 파일 수정, 작성자와 같은 세션 · 같은 입력 | 확인 수행 |
| **병합 봇** | 수준 1 · 2 관문에서 판정이 ✅뿐 + 반박 없음 + 자동 관문 통과(+ 수준 2면 사람 승인) | 병합, TASK `DONE` PR | 판정, 작성. 작성 에이전트와 다른 계정 | 반영 |
| **분류 자동화** | Issue 열림 | 라벨 · 담당자 지정(`assign-issue`, AI 아님) | 판단 | — |

- **판정은 '확인'뿐이다**(DDD 판정 3분류 확인 · 해석 · 선택). 원문이 모호 · 충돌 · 침묵하면 해석 후보와 근거만 내고, 채택은 사람(PO)이 한다. 작성 에이전트의 정본 초안도 후보이며, 선택 · 해석은 사람이 병합한 정본 PR로만 선다.
- **선택(결정)과 책임은 사람만 한다**(핵심규약 5-5, DDD L2). 사람 역할(하위 도메인 담당자 · 리뷰어 · 운영 책임자 · PO)은 그대로다.
- **총괄 에이전트의 조건 넷**(DDD L2):
  1. 쪼갠 TASK와 배정은 후보다. 책임자는 PM이며 TASK PR 병합이 확정이다. 병합 봇이 병합하게 되어도 책임자는 PM이다. 쪼갠 근거(바뀐 POL · 화면 코드)와 실행 증명을 PR 본문에 남긴다. 처음에는 수준 2로 시작한다.
  2. 판정 · 병합 · 정본 결정을 하지 않는다. 작성 대화를 판정 에이전트에 넘기지 않는다.
  3. 정본에 없는 규칙을 만들어 넣지 않는다. 막히면 질문 Issue로 사람에게 간다.
  4. 작업판 상태만으로 일하고 다른 에이전트와 대화하지 않는다. 작성 에이전트에게 주는 지시는 TASK 파일이 전부다.
- **판정 입력은 줄이기와 넣기가 함께다**: 작성 대화 · 중간 산출물은 빼고, 변경분 · 정본 절 · 계약 operation에 더해 정본 절이 인용한 상위 원문(법 · 계약 · 결정 기록)을 직접 넣는다(핵심규약 7절).

## 6. 검사 넷 (판정 에이전트)

| 검사 | 언제 | 무엇을 | 빠짐 · 모순이 나오면 |
| :--- | :--- | :--- | :--- |
| 정본 원문 대조 | 정본 PR | 고른 문안이 인용한 법 · 계약 · 결정 원문과 맞는지 | 질문 Issue(PO) |
| 구현 전 일관성 | 총괄 TASK PR(멀티부터) | TASK 묶음 · 정본 변경분 · 계약이 서로 모순되지 않는지(GitHub Spec Kit의 analyze와 같은 자리) | TASK를 잘못 쪼갠 것이면 PM이 고침, 해석 · 선택이면 질문 Issue(PO) |
| PR 판정 | 코드 PR | `/spec-check` 5등급 | 작성 에이전트가 고침(2회까지) |
| 변경 단위 취합 | 한 정본 변경의 TASK가 모두 닫힘(멀티부터) | 바뀐 정본 절 전체 ↔ 병합 결과 전체 | 빠진 규칙이면 보충 TASK 후보(PM 확정), 해석 · 선택이면 질문 Issue(PO) |

- 취합은 정본 변경분에서 POL · 화면 코드 목록을 먼저 기계로 뽑고 항목마다 판정한다(자유 종합 금지). 목록은 바닥이지 천장이 아니다. 목록 밖에서 본 것은 판정하지 않고 '목록 밖 발견'으로 적어 총괄이 보충 후보나 질문으로 가른다.
- PM이 TASK를 고치면서 정본 해석을 대신 정하지 않는다.
- **등급 A 규칙의 R2 확인(DDD R2)**: 위험 등급 A 규칙은 릴리스 전에 R2에 이르러야 한다. R2의 기준 구현은 하위 도메인 계산기(선택 부록 3절)가 있으면 그것, 없으면 실제 코드 경로 + 회귀 시나리오다. 등급 A는 둘 중 하나가 있어야 한다. 정답 시나리오의 기대값은 원문(법 · 계약 · 결정 기록)에서 손으로 세고, 구현을 돌려 나온 값을 기대값으로 삼지 않는다. R2 확인 수행자는 계산기 · 코드 작성자와 다르다(DDD V-10). 이 확인은 릴리스 판정의 조건이다(DDD methodology.md 70 · 71행).
- 취합 판정의 수준은 묶인 PR 가운데 가장 높은 수준이다. 릴리스 판정은 취합 결과를 근거로 쓰고, 취합이 없는 변경은 그것부터 돌린다.

## 7. 충돌을 막는 규칙 (셋)

1. **TASK 1건 = 실행 1개 = 브랜치 1개.** 열린 PR이 있는 TASK에 새 실행을 띄우지 않는다.
2. **같은 화면 코드는 한 번에 하나.** `screen_ids`가 겹치는 열린 PR이 있으면 뒤 TASK는 기다린다(대기 표시만).
3. **상태는 작업판에만.** 로컬 메모 · 대화 요약을 다음 실행의 입력으로 쓰지 않는다.

## 8. 멈춤과 사람 (장치 대신 백로그)

- **Blocking 질문**: 그 분기를 막고 나머지를 끝내 PR을 올린 뒤 끝난다. Issue가 닫히면 다시 깨어난다. 자동 재알림은 없다(핵심규약 9-6).
- **실패**: `agent-failed` 라벨과 한 줄 사유를 남기고 멈춘다. 자동 재시도는 없다. PM 백로그 항목이다.
- **고침 반복 상한**: 같은 PR을 고치는 것은 2회까지, 그 뒤 ❌면 `agent-failed`.
- **조용한 실패 보기**: 작성 에이전트에 배정됐는데 PR이 없는 TASK는 `open_tasks.md`에 표시해 주간 회의에서 본다.
- **사람 표본 검토**: 수준을 내린 뒤에도 주간 회의에서 판정 리포트 몇 건을 원기록에서 뽑아 본다. 9-8 뒤집힘 판단 재료다.
- **반박**: 반박이 남은 항목은 통과가 아니다. 사람에게 간다.
- **사후 되돌림(수준 1)**: 사람이 revert PR을 연다. 뒤집힌 일은 수준을 올리는 신호다(9-8).

## 9. 기록 · 비용 · 보안

- **실행 증명**: 모든 실행은 결과물에 수행자 계정, 모델 · 스킬 판, 대조 커밋, 사용 토큰을 한 줄로 남긴다. 같은 모델이면 '같은 모델'을 적는다. 형식은 도메인 규격 3이다.
- **비용**: 실행당 토큰 상한을 두고 넘으면 `agent-failed`로 멈춘다(값은 `실행_연결.md`).
- **계정 분리(최소 권한)**: 작성 · 판정 · 병합 봇은 서로 다른 계정이다. 작성은 브랜치 쓰기, 판정은 읽기와 코멘트, 병합 봇만 병합 권한. 비밀값은 Secrets에만 둔다(4-5).
- **입력 자료**: 실데이터 · 개인정보는 에이전트 입력에 넣지 않는다. 데이터 등급 기준은 DDD L3 '증거 기록'을 따른다. 실데이터 리플레이 같은 실행은 사람이 격리 환경에서 한다.

## 10. 도입 순서

1. 판정 에이전트(수준 3, 지금과 같은 효력). 판정 기록이 쌓여 수준을 내릴 근거가 된다.
2. 총괄 에이전트(수준 2).
3. 작성 에이전트(TASK가 그 계정에 배정될 때만).
4. 병합 봇(PO가 어떤 관문을 수준 1로 내릴 때).
5. 그 뒤(선택 부록 6절): 관측 자동 수집 · 평가 시나리오 · 지식 계층 · 실행 샌드박스.
